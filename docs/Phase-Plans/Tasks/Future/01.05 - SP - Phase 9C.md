## Arch Spec

### Spec Target

This implementation target is only:
- `[1.1C] SP - Phase 9C - Graph-Local Compile / Preview Preparation`

This cut is intentionally a bridge above the graph-document/browser foundation:
- each graph should keep its own compile/build memory
- each graph should keep its own preview-preparation memory
- shared worker/viewer infrastructure can stay shared
- the app should stop collapsing compile/build/preview state into one spaghetti-global bucket

If this cut is wrong, later work has no stable base for:
- `SP 10` graph-aware worker/result routing
- later `AS` output structure work
- Browser-aware graph output ownership

### Carry-Forward From `9A` And `9B`

Locked carry-forward rules from `9A` and `9B`:

- `useSpaghettiStore` remains the right home for graph + viewport runtime state
- `useAppStore` should stay shell/bridge-oriented and should stop owning spaghetti-global compile/build buckets over time
- graph-owned truth must stay graph-owned
- viewport/browser-owned state must stay out of graph-owned compile/build truth
- narrow temporary bridges are acceptable if they stay explicit and small

Working read:
- `9C` should build on graph documents and Browser/open-focus structure
- this phase expands graph-local runtime memory, not Browser UI or output hierarchy

### Problem Statement

After `9B`, the app has:
- graph documents
- Browser/open-focus viewport coordination
- explicit per-viewport graph binding

But it still does not have:
- graph-local compile/build memory
- graph-local preview-preparation memory
- graph-keyed bridge buckets through shared worker/viewer services

Current runtime still behaves too much like:
- one global spaghetti compile/build bucket in `useAppStore`
- one preview-prep path in `ViewerHost`
- one build-wiring branch keyed only by `inputMode === 'spaghetti'`

`9C` needs to make graph-local build/preview memory real without pulling in full routing or Browser-facing output hierarchy.

### Locked Direction

- `9C` is a bridge phase
- each graph owns its compile/build memory bundle
- each graph owns its preview-preparation bundle
- one worker lifecycle can stay shared
- one viewer shell can stay shared
- requests/results/preview-prep must be ready to route by `graphDocumentId`

### Locked Graph-Local Compile / Build Memory Bundle

Use this first-pass graph-local compile/build bundle:

- `lastCompileResult`
- `previousBuildInputs`
- `pendingChangedParamIds`
- `pendingStatsPartKeys`
- `pendingInstances`
- optional `lastBuildSeq`

Rules:
- this bundle is graph-local and graph-keyed
- it should no longer live as one spaghetti-global bucket in `useAppStore`
- it should be ready to hand off into later graph-aware request/result routing

### Locked Graph-Local Preview-Preparation Bundle

Use this first-pass graph-local preview-prep bundle:

- graph-local output declaration state
- graph-local preview candidate list
- graph-local source/build part identity mapping
- graph-local build-stats-ready part keys
- graph-local "what this graph is trying to preview" memory

Rules:
- each graph prepares its own previewable outputs locally
- richer Browser-facing output hierarchy comes later
- this phase is not finishing final output structure

### Locked Infrastructure Rule

- one shared worker lifecycle can stay shared
- one shared viewer shell can stay shared
- compile/build/preview-prep state still becomes graph-local and graph-keyed

Working rule:
- shared services do not need to fragment into one worker per graph or one viewer per graph
- but the state they process should be graph-scoped and ready to route by `graphDocumentId`

# Close Out notes

What landed cleanly:
- `useSpaghettiStore` is now the clear runtime home for graph-local compile/build and preview-preparation memory.
- `useAppStore` stayed in the bridge role, which was the right constraint for `9C`.
- shared worker lifecycle and shared viewer shell did not need to split apart to make graph-local runtime real.

What was actually harder:
- the hardest seam was not compile itself, it was the request/result bridge around shared worker build sequencing.
- the light `buildSeq -> graphDocumentId` tracking bridge was enough for `9C` without dragging full `SP 10` routing forward.
- preview-preparation was easier once it was treated as a reusable preparation bundle instead of one-off viewer logic.

Carry-forward notes:
- `SP 10` should own full request/result routing and remove the remaining active-graph bridge assumptions around worker results.
- later `AS` work should build on the graph-local preview-preparation bundle instead of recomputing Browser-facing output hierarchy from scratch.
- if future graph mutations start making compile/build buckets feel too stale between edits, that should be handled as a later policy refinement, not retrofitted back into `9C`.
