## Arch Spec

### Spec Target

This implementation target is only:
- `[3.2B-2] SP / NI / FS / GE - Main Viewport Sketch Rendering And Toolbar Split`

This cut intentionally sits:
- after the shipped `3.2A` `Geometry/Sketch` shell and `3.2B` draw/review flow
- before later depth such as direct viewport sketching, richer snapping, or body-feature growth

### Problem Statement

The first `3.2B` ship established the draw/review workflow, but the active sketch geometry is still rendered inside the floating sketch window instead of in the actual model viewport. That creates the wrong interaction frame and makes the sketch panel feel like the drawing canvas.

Without this correction:
- the floating window visually behaves like a mini-editor instead of a toolbar
- the user loses the intended sense that sketching belongs to the shared `Viewer`
- later viewer-driven sketch depth would be built on the wrong surface split

### Locked First-Pass Win

`[3.2B-2]` counts as real when:
- the floating sketch window stays visible as the command surface
- the actual authored geometry appears in `Viewer`
- review/highlight state also uses `Viewer`
- the large embedded preview card is removed instead of remaining as the primary render surface

Plain-English rule:
- the sketch window should control sketching, but `Viewer` should visibly be where sketching happens

### Locked Architecture Choice

`[3.2B-2]` is not an HTML/SVG-in-`ViewportOverlay` expansion.

It explicitly introduces:
- a real viewer-backed sketch overlay surface in `Viewer`
- a public `viewerBridge.ts` contract for sketch overlay sync
- `ViewerHost` as the bridge that reads store state and pushes viewer-ready overlay data into `Viewer`

It explicitly removes:
- the idea that `renderSketchPreview(...)` inside `ViewportOverlaySketchPreviewCard` is a valid long-term render host
- the large embedded preview card as a primary sketch surface

### Locked Surface Split

The corrected surface split is:

- floating sketch window:
  - tool buttons
  - numeric command entry
  - mode/context labels
  - confirm/cancel/review actions

- `Viewer`:
  - active sketch primitive rendering
  - selected-entity highlighting
  - profile-review highlighting
  - future-compatible overlay ownership for later viewer-driven sketch interaction

Ownership rule:
- the floating window owns command state
- spaghetti sketch state remains in the store
- `Viewer` owns visible sketch rendering and cleanup

Primary ownership split:
- `useSpaghettiStore` remains the source of truth for active session, active tool, `SketchFeature.components`, and selected profile id
- `ViewerHost` derives a render-only sketch overlay VM from current store state
- `Viewer` renders and clears overlay geometry but does not become the source of truth for sketch data
- `ViewportOverlay` keeps only window chrome, command inputs, mode labels, and review controls

### Locked Correction Boundary

This follow-up does not change the stored sketch data model.

It does not change:
- `Geometry/Sketch` as the user-facing node
- `SketchFeature.components` as the source of truth
- the current `Draw` and `Review` entry points in the node shell
- the selected-profile contract already established for downstream work

It changes only:
- where the sketch entities are drawn
- where review highlighting is shown
- the viewer-facing contract that receives sketch overlay state

### Locked Floating Window Rule

The floating sketch window should stop pretending to be the drawing surface.

Required behavior:
- no large embedded preview card as the primary visual sketch surface
- no implication that the user is drawing inside the floating panel
- enough contextual text to keep the user oriented to plane, mode, and selected tool
- keep profile-selection cards only as review controls, not as a substitute render surface

Locked requirement:
- remove the large embedded preview card entirely in this phase

### Locked Public Interface Change

`3.2B-2` should add one explicit viewer-facing contract instead of leaving the render API implicit.

Add in `src/app/viewerBridge.ts`:
- `GeometrySketchOverlayVm`
- `setGeometrySketchOverlay(overlay: GeometrySketchOverlayVm | null): void`

`GeometrySketchOverlayVm` should be a render-only payload containing:
- `mode: 'draw' | 'review'`
- `plane: 'XY' | 'XZ' | 'YZ'`
- `components`
- `profiles`
- `selectedProfileId`
- optional active-tool or selected-component context only if it is needed for first-pass highlight state

Contract rule:
- React/store side prepares the overlay VM
- `Viewer` only renders it
- profile derivation stays outside `Viewer`

### Locked Plane Mapping And Render Rule

The viewer overlay should render:
- authored line, arc, spline, rectangle, and circle output
- active selection highlighting
- profile-review highlighting
- plane-aligned sketch presentation consistent with the active `SketchPlane`

2D-to-3D mapping:
- `XY` maps `(x, y)` to `(x, y, 0)`
- `XZ` maps `(x, y)` to `(x, 0, y)`
- `YZ` maps `(x, y)` to `(0, x, y)`

First-pass viewer rendering rule:
- lines, arcs, splines, rectangles, and circles render as lightweight viewer overlay line geometry
- draw mode shows all authored components on the active plane
- review mode shows the same components plus profile highlighting
- selected profile highlight must use a distinct visual treatment from non-selected geometry
- this phase does not add click-to-draw, hit-testing, or manipulator editing in the viewport

### Implementation Order

Implement in this order:

1. remove the large preview-card-first assumption from `ViewportOverlay.tsx`
2. add `GeometrySketchOverlayVm` and `setGeometrySketchOverlay(...)` in `viewerBridge.ts`
3. build the sketch overlay VM in `ViewerHost` from current store/session state
4. add viewer-side overlay groups, materials, render updates, and cleanup in `Viewer.ts`
5. render active sketch components in draw mode
6. render profile highlighting in review mode
7. keep the floating sketch window controls-only
8. verify session close/open clears and restores viewer overlay state correctly
