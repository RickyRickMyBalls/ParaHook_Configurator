## Arch Spec

### Spec Target

This implementation target is only:
- `[1.1A.3] SP - Phase 9A.3 - Viewport Binding And First Singleton Split`

This cut is intentionally narrow:
- introduce explicit editor viewport identity
- bind that viewport to one `graphDocumentId`
- stop assuming one editor instance equals one graph
- keep the app running with only one live spaghetti viewport in practice

If this cut is wrong, later work has no stable base for:
- `9B` Browser-managed multi-editor behavior
- focused/open viewport coordination
- graph switching by editor viewport
- later project-level graph navigation

### Problem Statement

After `9A.1` and `9A.2`, graph identity and graph-owned authored canvas truth are now explicit, but the editor surface is still shaped like a singleton app mode.

Current runtime shape:
- `AppShell` only renders one floating spaghetti window when `inputMode === 'spaghetti'`
- floating window position and size live locally in `AppShell`
- `SpaghettiPanel` has no explicit viewport identity or `graphDocumentId` binding
- `SpaghettiEditor` reads the active graph but is not explicitly told which graph document it is a viewport into
- `useSpaghettiStore` owns graph document identity, but editor viewport identity does not exist yet
- `useAppStore` compile/build flow still depends on the active graph seam

That means the current editor runtime still blurs:
- graph truth
- active app mode
- one specific panel/window instance
- the bridge between editor identity and graph identity

`9A.3` needs to separate those concerns without pulling in Browser ownership, graph switching UX, or graph-local routing work.

### Locked Runtime Placement

Lock these first-pass runtime placements:

- `GraphDocument` ownership remains in `useSpaghettiStore`
- the first `EditorViewport` container also lives in `useSpaghettiStore`
- `useAppStore` keeps temporary app-shell mode state and current compile/build bridge behavior
- `AppShell` remains the shell that decides whether the floating spaghetti surface is rendered, but it is not the owner of graph identity

Lock this first-pass store shape:

```ts
type EditorViewport = {
  editorViewportId: string
  graphDocumentId: string
  isFocused: boolean
  windowMode: 'floating'
}

type SpaghettiViewportState = {
  editorViewportsById: Record<string, EditorViewport>
  editorViewportOrder: string[]
  activeEditorViewportId: string
}
```

Rules:
- only one viewport needs to exist in `9A.3`
- `position`, `size`, and `z-order` stay local to `AppShell` in this phase
- `activeGraphDocumentId` remains temporarily in the store as a compatibility bridge and must mirror the active viewport binding
- `9B` is the phase that makes viewport coordination first-class

### Current Execution Rules

Code-grounded rules for this cut:

- `useSpaghettiStore.graph` can no longer stand in for both graph truth and editor binding truth
- `useSpaghettiStore` is the correct home for the first viewport-binding seam because it already owns graph document identity
- `useAppStore` should not become the owner of editor viewport records in `9A.3`
- `inputMode` may remain temporary, but only as app-level UI mode state
- `AppShell` is currently a one-window seam and must stop being the only place where spaghetti identity exists
- `SpaghettiPanel` and `SpaghettiEditor` should become consumers of viewport binding, not owners of graph identity

### Seams To Break In 9A.3

This cut only needs to break these seams:

1. one floating spaghetti window cannot remain equivalent to one graph
2. editor runtime cannot infer graph identity only from one active global graph
3. `SpaghettiPanel` cannot stay unbound to viewport identity
4. `SpaghettiEditor` cannot stay unbound to `graphDocumentId`
5. app-global spaghetti UI mode cannot continue acting like the long-term editor ownership seam

Follow-on note:
- multi-viewport focus rules, z-order, Browser coordination, and graph dropdown switching belong to `9B`, not this cut

### Canonical `9A.3` Viewport Contract

Lock this first-pass viewport contract:

```ts
type EditorViewport = {
  editorViewportId: string
  graphDocumentId: string
  isFocused: boolean
  windowMode: 'floating'
}
```

Rules:
- `editorViewportId` is required and stable
- `graphDocumentId` is required and is the graph-binding key
- `isFocused` is viewport state, not graph-authored truth
- `windowMode` is viewport state, not graph-authored truth
- position / size / z-order may stay local or deferred in this phase if that keeps the cut smaller

### Binding Flow

Lock this first-pass binding flow:

- `AppShell` reads `activeEditorViewportId`
- `AppShell` passes `editorViewportId` into `SpaghettiPanel`
- `SpaghettiPanel` resolves the bound `graphDocumentId`
- `SpaghettiPanel` passes both `editorViewportId` and `graphDocumentId` into `SpaghettiEditor`
- `SpaghettiEditor` stops using `selectActiveGraph` as its ownership seam and instead reads the graph by the explicit `graphDocumentId`

Lock these minimum selectors/helpers:
- `selectActiveEditorViewport`
- `selectEditorViewportById`
- `selectGraphDocumentById`
- `selectGraphByDocumentId`

Lock these minimum prop shapes:

```ts
type SpaghettiPanelProps = {
  editorViewportId: string
}

type SpaghettiEditorProps = {
  editorViewportId: string
  graphDocumentId: string
  showHeaderControls?: boolean
}
```

### Temporary Compatibility Rule

Choose this temporary bridge behavior for `9A.3`:

- `activeGraphDocumentId` remains usable in `9A.3`
- the active viewport binding becomes the new explicit editor seam
- store actions must keep `activeGraphDocumentId` synchronized with the active viewport's `graphDocumentId`
- compile/build entrypoints in `useAppStore` remain no-arg and continue to use the active graph document in `9A.3`
- sample-load actions in `SpaghettiPanel` can remain active-graph scoped in `9A.3`

Why:
- this keeps `9A.3` out of `9C` and `SP 10`
- it allows the editor-binding seam to become explicit before compile/build memory is graph-keyed later

### `9A.3` Decision Defaults

#### editor viewport identity

Decision:
- editor viewports should point at graph documents by id

#### graph truth vs viewport truth

Decision:
- graph truth remains graph-owned
- editor viewport state does not belong inside graph truth

#### one-window spaghetti assumption

Decision:
- the one-window spaghetti assumption is a transitional seam that must be weakened in `9A.3`

#### first viewport container location

Decision:
- place the first viewport container in `useSpaghettiStore`, not `useAppStore`

Why:
- graph document identity already lives in `useSpaghettiStore`
- `useAppStore` should stay temporary for app-shell mode and compile/build bridge behavior in this phase

#### `inputMode`

Decision:
- retain temporarily as UI mode state only

#### `viewMode`, `focusNodeId`, and similar local editor state

Decision:
- keep viewport-local in `9A.3`

Why:
- these states describe how one editor surface is currently being read or inspected
- they should not be promoted into graph truth in this cut

#### multi-viewport coordination

Decision:
- defer to `9B`

Why:
- `9A.3` should only establish the first explicit viewport binding seam
- Browser-managed coordination belongs to the next phase

### Current Seam Findings

#### `AppShell.tsx`

Current seam:
- owns one floating window position/size locally
- renders spaghetti only when `inputMode === 'spaghetti'`
- has no viewport record or viewport id

Implication for `9A.3`:
- `AppShell` should render the spaghetti surface through `activeEditorViewportId`
- local floating window position/size can remain local in this phase

#### `useSpaghettiStore.ts`

Current seam:
- already owns graph document identity
- still exposes `selectActiveGraph`
- has no viewport container yet

Implication for `9A.3`:
- this is the correct home for the first viewport-binding seam
- the store should add document-by-id and viewport selectors
- `selectActiveGraph` can survive temporarily as a compatibility bridge

#### `useAppStore.ts`

Current seam:
- compile/build bridge still depends on active graph selection
- `inputMode` still gates legacy vs spaghetti behavior
- the store does not currently own graph document truth

Implication for `9A.3`:
- do not move viewport records into `useAppStore`
- keep compile/build entrypoints active-graph scoped for now

#### `SpaghettiPanel.tsx`

Current seam:
- assumes one global editor surface
- sample-load / compile / build actions are still active-graph scoped
- there is no explicit `editorViewportId`
- there is no explicit `graphDocumentId` prop

Implication for `9A.3`:
- the panel should attach to the viewport seam instead of assuming one global graph/editor
- sample-load / compile / build actions can remain active-graph scoped in this phase

#### `SpaghettiEditor.tsx`

Current seam:
- currently uses `selectActiveGraph`
- has local `viewMode`, `focusNodeId`, and `newPartType`
- is not explicitly passed the graph document identity it is viewing

Implication for `9A.3`:
- keep local editor presentation state local
- make graph binding explicit through `graphDocumentId`

# Close Out notes

### What Worked

- the cleanest first viewport seam was `useSpaghettiStore`, not `useAppStore`
- keeping `activeGraphDocumentId` as a synced bridge let the editor-binding cut land without dragging compile/build routing into the same refactor
- explicit prop flow from `AppShell -> SpaghettiPanel -> SpaghettiEditor` was enough to make graph binding real in the editor path without redesigning the whole spaghetti runtime

### What We Learned

- `SpaghettiEditor` was not the only hidden active-graph consumer; `ExpandedEditor`, `CollapsedEditor`, and `SpaghettiCanvas` also needed explicit graph-document binding
- the current compile/build bridge can stay active-graph scoped a little longer, but the explicit viewport seam is now in place for later graph-keyed routing work
- local editor state such as `viewMode`, `focusNodeId`, `newPartType`, and window size/position did not need to move for `9A.3`

### Watch Outs For Later Phases

- `selectActiveGraph` still exists as a compatibility seam outside the editor path and should be narrowed further in later work
- `selectedNodeId`, `selectedEdgeId`, `hoveredEdgeId`, and related canvas interaction state are still single-surface state; that is acceptable for `9A.3` but becomes a blocker once multiple live viewports exist
- `AppShell` still owns floating window size/position locally; that is correct for this cut, but `9B` will need to decide when those move into viewport-managed state

### Next Phase Handoff

- `9B` should own:
  - multiple live editor viewports
  - focus and z-order rules
  - Browser-coordinated open/focused viewport behavior
  - graph switching UX
- `9C` should own:
  - graph-local compile/build memory
  - graph-local preview-prep memory
  - further reduction of active-graph compatibility seams
