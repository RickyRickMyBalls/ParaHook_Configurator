## Arch Spec

### Spec Target

This implementation target is only:
- `[3.2D] SP / NI / FS / GE - Loft Foundation`

This cut intentionally sits:
- after the first profile-to-solid baseline in `[3.2C]`
- before the later broader feature-node growth in `Sweep`, `Boolean`, `Fillet`, `Shell`, and beyond

### Problem Statement

The foundational geometry lane needs one honest follow-up body feature after `Extrude` so ParaHook can prove it is not limited to only the simplest prismatic path.

Without this cut:
- the first body-feature language stays too narrow
- more organic profile transitions remain planning-only
- later ParaHook-specific loft-driven feature growth has no stable first contract

### Locked First-Pass Win

`[3.2D]` counts as real when:
- `Loft` exists as a real user-facing node
- the first contract can take the minimum required profile inputs and produce one `SolidBody`
- the node remains intentionally constrained instead of collapsing into advanced lofting depth

Plain-English rule:
- make the next honest profile-based body feature real, but keep it small

## Current Questions To Detail Next

### Q1. What exact `LoftType` enum values should exist in the first shipped contract?

Suggested answer:
- first public `LoftType` should be `Basic` only
- `RailGuided` should stay explicitly later

Why:
- the current feature stack only has real `sketch`, `closeProfile`, and `extrude` feature types
- there is no honest general-purpose loft op in `featureTypes.ts`, `featureSchema.ts`, `compileFeatureStack.ts`, or `featureStackRuntime.ts`
- adding `RailGuided` now would create a broader public promise before the first plain profile-to-profile loft path exists

Planning rule:
- `[3.2D]` should prove the second honest body feature, not ship advanced surfacing vocabulary early

### Q2. What profile inputs should the first honest `Loft` contract require?

Suggested answer:
- first public loft contract should require:
  - `StartProfile`
  - `EndProfile`
  - one `out:SolidBody - [SolidBody]`
- do not require rails, guides, intermediate profiles, or continuity controls in the first cut
- later, a lightweight `Intermediate Profiles` control can be added as a numeric `[Float]`-style value that ParaHook rounds/clamps to a whole-number count and uses to generate evenly spaced internal sections between `StartProfile` and `EndProfile`

Why:
- this is the smallest shape transition that materially expands beyond `Extrude`
- it matches the existing planning direction in `Spaghetti-Types.md`
- anything larger makes `[3.2D]` compete with later sweep/advanced lofting phases instead of finishing the foundation lane
- a generated intermediate-count control is much cheaper than supporting fully authored intermediate profile inputs in the first contract
- if this appears later, it should behave like an integer count even if the underlying numeric transport still uses the existing `[Float]`/number-expression style

Planning rule:
- start from two selected profiles in, one solid body out
- treat generated `Intermediate Profiles` count as a later optional smoothing/density control, not a required first-pass input

### Q3. Should `Loft` consume raw sketch outputs directly, or reuse the selected-profile seam?

Suggested answer:
- `Loft` should consume selected downstream-ready profiles, not raw unresolved sketch geometry
- under the hood, first implementation should preserve the same `closeProfile -> profileRef` style compatibility seam used by `Extrude`

Why:
- `3.2B` already moved profile choice into the `Sketch` experience from the user perspective
- `3.2C` already locked the first body-feature compatibility path around selected profiles
- reusing that seam keeps `Loft` aligned with the existing source-of-truth flow instead of inventing a second profile-resolution model

Planning rule:
- from the user view: pick finished profiles
- under the hood: keep the selected-profile compatibility seam until a broader geometry-node refactor replaces it honestly

### Q4. Is `RailGuided` part of the first honest cut or explicitly later?

Suggested answer:
- explicitly later

Why:
- the existing `railMath` and `toeLoft` types in `spaghettiTypes.ts` and `nodeRegistry.ts` are older part-node/driver seams, not a real general loft-feature implementation
- there is no generic rail authoring, rail selection, or rail-aware worker runtime path yet
- folding those legacy ports into `[3.2D]` would blur two different systems and make the new loft contract less honest

Planning rule:
- keep `[3.2D]` separate from legacy `toeLoft`/driver-node language
- treat real rail-guided lofting as a later follow-up after plain loft exists cleanly

### Q5. What should count as the first real `[3.2D]` proof target?

Suggested answer:
- one managed `Sketch`
- one second managed `Sketch`
- one selected profile from each
- one `Loft` node
- one resulting `SolidBody`

Why:
- that proves ParaHook can transition between two authored profile sections instead of only extruding one profile along depth
- it keeps the proof smaller than advanced lofting, but more meaningful than another extrusion variant

Planning rule:
- `[3.2D]` succeeds when `Sketch -> Loft -> SolidBody` is real with two selected profiles

### Q6. What should the first `Loft` output surface look like?

Suggested answer:
- one main output: `out:SolidBody - [SolidBody]`
- keep helper geometry, section wires, and internal surfacing artifacts private

Why:
- this matches the same user-facing body contract already locked for `Extrude`
- helper/result-splitting would widen the public surface before the base loft behavior is stable

Planning rule:
- first loft result should be one clean solid-body output

### Q7. What current code seams need to change before `Loft` can fit honestly?

  - add a real `LoftFeature` type and input/output contract

Planning rule:
- `[3.2D]` needs aligned type/schema/UI/compiler/runtime work from the start, or the node contract will drift immediately

### Q8. What should stay explicitly out of scope for the first loft cut?

Suggested answer:
- defer:
  - `RailGuided`
  - intermediate profiles
  - continuity controls
  - twist-like deformation options
  - open-surface loft modes
  - viewer-side rail editors

Why:
- those are the fastest ways for `[3.2D]` to turn from a foundational body feature into an advanced surfacing sinkhole
- none of them are required to prove the first honest `Loft` contract

Planning rule:
- finish the plain two-profile solid loft before expanding the surface language
