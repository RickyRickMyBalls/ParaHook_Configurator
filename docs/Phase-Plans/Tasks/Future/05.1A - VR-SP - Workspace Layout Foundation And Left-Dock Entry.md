## Doc Body

### Summary

`5.1A` establishes the shared shell foundation for workspace modes.

This phase should deliver:
- one app-level `Hybrid Workspace` system
- one canonical pane tree for tiled layout
- one required `Model Viewer` anchor region
- one first tiled-entry control using the existing left-dock `[]` button
- one default entry state that only splits out the left dock while leaving the main model viewport intact

### Locked Outcome

At the end of `5.1A`, ParaHook should have a locked architecture target for workspace layout ownership:
- the workspace system is not feature-local
- the workspace system is not Spaghetti-only
- `Windowed` and `Tiled` are placement styles of one shared system
- the first tiled entry uses the already-shipped left-dock split affordance

Important rule:
- `5.1A` defines the shell model and its first entry seam
- it does not yet need full pane-authoring UX depth

### Locked Model

The workspace system should be described as:
- one `Workspace Layout System`
- with two placement styles:
  - `Windowed`
  - `Tiled`

Important rule:
- these are not global app modes
- they are surface-placement styles inside one hybrid workspace

### Locked State Ownership

The first shared owner should live near `AppShell`, not in a feature store.

Recommended ownership:
- `AppShell`
- plus a dedicated workspace-layout state surface under:
  - `src/app/workspace/`

Avoid:
- putting the layout tree into `useSpaghettiStore`
- making workspace layout an accidental side effect of editor viewport state

### Locked Tile-Tree Shape

The canonical tiled-layout model is a tree.

Branch node owns:
- split direction
- split ratio
- split priority

Leaf node owns:
- hosted tool-surface instance identity
- pane-local metadata

This should be the minimum planned type family:
- `WorkspaceLayoutState`
- `WorkspacePaneNode`
- `WorkspaceBranchNode`
- `WorkspaceLeafNode`
- `WorkspaceSurfaceKind`
- `WorkspacePresentationMode`
- `ActiveWorkspacePaneId`

### Locked Viewer Anchor Rule

The first pass should require at least one main `Model Viewer` region.

Rules:
- the workspace must keep one protected main viewer alive
- the workspace may allow additional `Model Viewer` panes
- the first split anchors against that viewer region
- the user should not be able to accidentally remove the last remaining protected viewer in `5.1A`

Why:
- too much of the current app still assumes one honest 3D working area
- allowing additional model-viewer panes keeps the foundation aligned with the broader custom-workspace direction

Multi-viewport rule:
- additional `Model Viewer` panes should be cloned views of the same shared 3D workspace
- they should not create separate independent viewer worlds
- shared scene truth should stay unified:
  - objects
  - selection
  - transforms
  - loaded content
- pane-local viewer state may differ:
  - camera
  - projection/display mode
  - local viewer presentation toggles

### Locked Left-Dock Entry Rule

The existing `[]` left-dock split button becomes the first tiled-entry control.

Entry behavior:
- split out the current left-dock region
- keep the main model viewport intact
- treat that state as the clean first visible proof of the shared workspace system

Important clarification:
- the current stacked `Browser` plus `meatball editor` left-dock split is an interim proof
- the intended honest tiled target is:
  - one `Browser/title` pane
  - one `meatball editor` pane
  - one main `Model Viewer` pane
- `5.1A` should therefore avoid encoding the grouped left dock as the permanent final pane model

Important rule:
- do not invent a second new entry control before this one is reused

### Active Pane Rule

The shared workspace should define one active tiled pane.

Active pane should own:
- keyboard-targeted layout actions
- focus-sensitive workspace actions
- contextual pane/surface commands

Important rule:
- active-pane ownership belongs to the shell, not any one feature surface

### Pane Header Slot Rule

Every tiled pane should reserve a top-left `switch viewport type` slot.

This control should:
- behave like the Blender-style viewport-type switcher
- live in a stable position at the top-left of each pane
- open a menu of supported tool-surface options for that pane
- let the user change the current pane from one hosted surface to another

Important boundary:
- `5.1A` locks the existence and placement of this control as part of the shell model
- the exact first-pass menu contents and hosting policies still belong mainly to `5.1C`

### Still Needed Decisions And Suggested Answers

#### `5.1A.Q1` - Where should the first real workspace owner live?

Locked answer:
- create a dedicated workspace seam under `src/app/workspace/`
- keep the state owner app-level and shell-owned near `AppShell`
- let `useAppStore` reference workspace state only if needed for broad app coordination

Why:
- this keeps workspace ownership out of `useSpaghettiStore`
- this avoids turning the shell model into feature-local editor state
- this gives later `5.1C` and `5.1D` work a stable home

#### `5.1A.Q2` - Should the first tile tree allow only one required viewer leaf?

Locked answer:
- yes for the first pass, but only as a minimum rule
- require at least one protected `modelViewer` leaf
- allow additional `modelViewer` leaves
- do not allow the user to delete the last remaining protected viewer during `5.1A`

Important clarification:
- additional `modelViewer` leaves are clones of the same shared workspace view
- they are not separate scene/runtime instances

Why:
- the current app still assumes one honest 3D working area
- protecting the main viewer avoids early shell states that break the rest of the workspace

#### `5.1A.Q3` - What exactly does the left-dock `[]` button create?

Recommended answer:
- treat it as `Enter First Tiled Layout`
- it should create the simplest shared layout proof:
  - one protected `modelViewer` pane
  - one tiled left-dock pane
- do not let the button create a second special-case shell branch

Why:
- this reuses an affordance the app already teaches
- it gives `5.1A` one clear first-entry layout without needing full pane-authoring depth

#### `5.1A.Q4` - What should the left-dock pane host in that first entry state?

Recommended answer:
- treat the current grouped left dock as an interim transition shape, not the target end state
- the target first honest tiled layout should be:
  - one `Browser/title` pane
  - one `meatball editor` pane
  - one `Model Viewer` pane
- if implementation needs a short bridge step, it can reuse the grouped left-dock host briefly
- but the architecture should already assume `Browser` and `meatball editor` become separate panes with a horizontal split between them

Why:
- the real workspace target is no longer one left-dock viewport with stacked content
- `Browser` and `meatball editor` already read like separate working surfaces
- the foundation doc should describe the intended pane model honestly, even if the code reaches it through a short bridge step

#### `5.1A.Q5` - How strict should the first tile-tree schema be?

Recommended answer:
- keep it minimal and explicit
- one discriminated union:
  - `branch`
  - `leaf`
- one branch always has exactly two children
- one leaf always hosts exactly one surface instance id

Why:
- binary split trees match the current split proof and are easy to reason about
- more flexible grid/container abstractions can come later if they are ever needed

#### `5.1A.Q6` - Does `5.1A` need floating/windowed rect state already?

Recommended answer:
- no
- `5.1A` only needs the shared placement model and tiled foundation
- defer floating-rect persistence and richer placement restoration to `5.1D`

Why:
- mixing persistence concerns into foundation work will make the first workspace owner harder to land cleanly

#### `5.1A.Q7` - What should active-pane ownership control in the first pass?

Recommended answer:
- keep it narrow
- active pane should only own:
  - shell focus
  - keyboard-targeted layout actions
  - future pane-context targeting
- do not let `5.1A` redefine tool-local focus behavior yet

Why:
- this gives the shell one honest active-pane concept without destabilizing existing feature focus rules

#### `5.1A.Q8` - What should be explicitly out of scope even if the tile tree exists?

Recommended answer:
- keep these out of `5.1A`:
  - pane header surface swapping
  - clone-versus-move hosting rules
  - divider context menus beyond what `5.1B` already proved
  - persistence and saved workspace modes
  - multi-window editor growth

Why:
- `5.1A` should be the shell-foundation cut, not the whole workspace feature at once

#### `5.1A.Q9` - Should every tiled pane have a Blender-style viewport-type switcher?

Recommended answer:
- yes
- every tiled pane should have a top-left `switch viewport type` control
- clicking it should open a list of supported pane/surface types the user can swap into that pane

Why:
- this matches the custom-workspace behavior you want
- it gives each pane one obvious identity/control point
- it keeps pane switching as a first-class shell action instead of hiding it in ad hoc right-click menus

First-pass rule:
- lock the control location and existence in `5.1A`
- lock the exact menu contents and allowed surface swaps in `5.1C`
