This phase covers:
- one calm shared row model for Browser-local interaction
- lightweight Browser selection state
- row-state affordances and small right-aligned row controls
- graph-document rows
- published graph-output rows
- open viewport rows

This phase does not cover:
- viewer emphasis behavior
- editor focus movement beyond existing explicit actions
- shared-viewer coordination or composition state
- `Content` branch rework
- deeper `Component / Object / Part` hierarchy
- build bars
- materials, visibility, or reference controls
- richer context-menu density

Working scope rule:
- `2.1A` should make the Browser rows feel intentional and consistent without taking over viewer or editor coordination

### Problem Statement

Lane `[1]` made the Browser structurally honest:
- graph rows exist
- graph rows expand
- published graph outputs are visible
- open viewports are visible

But the Browser rows still behave too much like:
- graph-specific button rows
- mixed one-off layouts
- Browser actions that are shaped per section instead of by one shared row model

`2.1A` needs to make the Browser feel like an intentional workspace shell by introducing one shared row anatomy and Browser-local interaction model without reopening editor-focus or shared-viewer coordination work.

### Locked First-Pass Browser Workspace Win

`2.1A` counts as real when:
- the Browser stops feeling like a set of ad hoc row layouts
- current graph-focused rows share one calm row anatomy
- the Browser has lightweight local selection state
- row controls become consistent, small, and secondary to the hierarchy

This phase does not need to make the Browser fully feature-complete.

Plain-English rule:
- make the Browser feel organized and usable before making it smarter

### Locked Row Rollout

The first `2.1A` rollout is:
- graph-document rows
- published graph-output rows
- open viewport rows

Do not pull into the first rollout:
- `Content` branch restructuring
- project-content rows beyond staying visually compatible with the rest of the Browser

Why this cut is correct:
- these rows already form the active graph-focused workspace surface
- they are the rows most affected by the inconsistent current layout
- `Content` should stay mostly unchanged until later output/content phases

### Locked Row Anatomy

Every upgraded Browser row should follow one shared anatomy:
- `[Expand] [Type Icon] [Name / Label] [State] [Controls]`

Working rules:
- the row is the control surface
- controls belong on the row, not below it
- controls stay:
  - small
  - right-aligned
  - secondary to the hierarchy
- rows without children may omit the expand affordance while still preserving alignment

The first-pass shared row contract should expose enough UI shape for this layout:
- stable `rowId`
- row kind/type
- label
- state/meta text
- selection state
- expandability/expanded state where relevant
- row-local actions metadata where needed

### Locked Browser-Local Interaction State

`2.1A` may introduce Browser-local interaction state for:
- selected Browser row/item id
- hover/active row affordances
- local expansion state
- row-local action availability

`2.1A` must not create new ownership truth for:
- project content
- graph publication
- shared-viewer composition
- editor focus
- durable project-file data

Plain-English rule:
- the Browser may own interaction context, not truth

### Locked First-Pass Row Actions

`2.1A` should preserve and normalize existing explicit row actions where they already exist:
- graph row:
  - `Save`
  - `Open`
  - `New Editor`
  - `Swap Editor`
- published output row:
  - no heavy new action surface in this cut
- viewport row:
  - keep existing explicit viewport actions if they already exist in the current Browser

`2.1A` may add:
- single-click Browser selection
- clearer row-state affordances
- improved visual consistency for existing actions

`2.1A` must not add:
- viewer emphasis behavior
- editor retargeting beyond existing explicit actions
- shared-viewer composition actions
- heavy context menus
- rename/delete/material/build controls

### Current Seam Findings

`BrowserPanel.tsx`
- currently mixes:
  - section layout
  - row layout
  - action buttons
  - local expansion state
- graph rows are action-heavy and section-specific rather than driven by a shared row contract
- `Content` is already separate and should not be pulled into this first `2.1A` cut

`selectBrowserGraphRows.ts`
- already provides the graph-focused Browser read surface
- currently returns graph-row and published-output-row view models
- does not yet define one shared Browser row contract across graph, published-output, and viewport row kinds

`expandedGraphDocumentIds`
- already exists as local Browser UI state
- should remain local in `2.1A`
- should not be converted into project or graph ownership truth

### Implementation Order

1. Introduce a shared Browser row view-model contract for the first graph-focused row kinds.
2. Refactor `BrowserPanel` to render graph rows, published output rows, and viewport rows through one shared row anatomy.
3. Add lightweight Browser-local row selection state.
4. Preserve existing explicit graph actions within the new row layout.
5. Keep `Content` functionally unchanged except for any necessary compatibility styling/alignment.
6. Stop before any viewer emphasis, editor-focus, or shared-viewer coordination behavior.

`2.1A` is complete when:
- graph rows, published output rows, and viewport rows render with one shared row anatomy
- single-click Browser selection updates only Browser-local state

- selecting a row does not trigger viewer emphasis or shared-composition changes
