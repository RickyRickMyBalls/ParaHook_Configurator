## Doc Body

### Summary

`5.0` is the cleanup bridge before `5.1`.

The goal is:
- reduce shell clutter that is taking up prime left-dock space
- make the app easier to read before broader workspace layout changes begin
- avoid dragging obvious legacy panels forward as if they are permanent first-class tool surfaces

Important rule:
- `5.0` should be narrow and tactical
- it should not turn into the final legacy purge lane

Recommended read:
- `5.0` is now large enough that it should be thought of as a small subphase family, not one single undifferentiated cleanup blob

### Locked Outcome

At the end of `5.0`, ParaHook should have a cleaner left-dock shell:
- `Preview Mode` no longer dominates permanent vertical space
- `Parts List` has an explicit future direction instead of remaining ambiguous shell clutter
- `Box Params` no longer sits as a large always-open legacy card unless still truly required
- the path into `[5.1] Workspace Modes` is clearer because the left dock is not still crowded by transitional panels

### Problem Statement

The current left dock is carrying too much transitional UI:
- `Preview Mode`
- `Parts List`
- `Box Params`

That creates several problems:
- the Browser loses visual priority
- the left dock feels crowded before the workspace system even starts
- legacy and future shell patterns are mixed together in one stack

Plain-English problem:
- too much vertical space is being spent on panels that may not deserve permanent first-class shell presence anymore

### Cleanup Target 1 - `Preview Mode`

Current read:
- `Preview Mode` is one of the strongest candidates for reduction because it looks like transitional mode UI rather than a long-range panel surface

Recommended direction:
- do not keep it as a large always-open left-dock card if that can be avoided

Good likely outcomes:
- collapse it into a compact row
- move it into a Browser-adjacent menu or lighter shell control
- hide it by default if it is still needed only occasionally

Important rule:
- keep the needed mode-switch behavior if the app still depends on it
- reduce the permanent shell footprint even if the behavior remains

Recommended removal order:
- first make `spaghetti` the default startup path
- then remove the visible `Legacy / Spaghetti` branch UI from `Preview Mode`
- then phase down or remove leftover legacy-only shell surfaces such as `Box Params`

Why:
- `Preview Mode` is still attached to real `inputMode` branching in the app
- changing startup default first is safer than deleting the branch UI first and discovering the app still boots into the old path

### Cleanup Target 2 - `Parts List`

Current read:
- `Parts List` might still be useful, but it should stop living as an unquestioned permanent card if its long-range ownership is not the left-dock stack itself
- for `5.0`, the immediate shell goal is to hide it from the left dock entirely, just like `Preview Mode`

Still-needed decision:
- is `Parts List` becoming:
  - part of `Browser`
  - a later dedicated hosted tool surface
  - or transitional legacy shell UI that should be reduced

Recommended direction:
- decide its destination before `[5.1]` hardens the broader shell model
- remove `Parts List` from the default left-dock stack entirely in `5.0`
- if any of its behavior still matters, preserve that behavior somewhere lighter instead of keeping the big left-dock card alive

Important rule:
- `5.0` does not have to finish the final long-range home of `Parts List`
- it does need to stop the current ambiguous "large permanent card by default" behavior from blocking shell cleanup

### Cleanup Target 3 - `Box Params`

Current read:
- `Box Params` is the strongest candidate for demotion or phase-down if it is still mostly legacy-oriented
- for `5.0`, the immediate shell goal is to hide it from the left dock entirely

Recommended direction:
- shrink it
- hide it behind explicit entry
- or phase it down from the default shell if it no longer represents the main future workflow
- remove `Box Params` from the default left-dock stack entirely in `5.0`
- if any of its behavior still matters, preserve that behavior somewhere lighter instead of keeping the big left-dock card alive

Important rule:
- do not delete still-needed parameter editing blindly
- do remove its permanent shell dominance if it is only a transitional workflow surface now

### Relationship To `[5.1] Workspace Modes`

`5.0` exists to help `[5.1]`, not compete with it.

`5.0` should:
- reduce shell clutter
- simplify the default left-dock stack
- make the future workspace layout transition easier

`5.0` should not:
- implement the pane-tree system
- implement tiled/windowed hosting
- absorb divider authoring or workspace persistence

Plain-English rule:
- `5.0` clears the stage
- `5.1` builds the new workspace system

### Recommended Subphase Breakdown

One good way to split `5.0` is:

#### `[5.0A]` - `Spaghetti Default Startup And Preview-Mode Shell Removal`

- make `spaghetti` the default startup path
- stop exposing `Legacy / Spaghetti` as the default visible branch choice
- hide or remove the `Preview Mode` card from the left dock
- keep legacy code alive underneath for the moment if needed

#### `[5.0B]` - `Legacy Left-Dock Panel Reduction`

- hide `Parts List` from the left dock
- hide `Box Params` from the left dock
- preserve any still-needed behavior somewhere lighter
- clarify whether any remaining useful behavior belongs in `Browser`, another lightweight surface, or a later hosted tool surface

#### `[5.0C]` - `Legacy Input-Mode Branch Removal`

- remove `inputMode: 'legacy' | 'spaghetti'` branching once `spaghetti` is the only real startup/input path
- delete the visible mode-toggle seam completely
- clean up remaining `legacy` conditionals in app state, viewer routing, build routing, and left-dock panel rendering
- treat this as the subphase that actually removes the legacy input path from code, not just from the UI

Important rule:
- `5.0A` and `5.0B` can land before `5.0C`
- deleting the legacy input branch should be its own explicit cleanup cut

#### `[5.0D]` - `Deferred Legacy Residue And Dead-Surface Cleanup`

- clean up everything intentionally left behind after `5.0A-C`
- remove dead shell-panel files and stale styling if they no longer have a future owner
- decide whether `parts` versus `assembled` is still a real viewer concept or leftover residue
- prune stale tests, imports, and output-list helpers that only existed to support removed panel-era surfaces

Important rule:
- `5.0D` should usually not block `[5.1]`
- it exists so the repo does not carry ambiguous "maybe dead, maybe real" residue forever

#### `[5.0E]` - `Spaghetti Editor Surface Standardization And Viewport-Type Cleanup`

- standardize what the full `Spaghetti Editor` surface is before `5.1` hardens viewport-type naming
- decide what the `meatball editor` is:
  - compact editor presentation
  - separate viewport type
  - or temporary shell bridge
- clean up editor-family terminology so pane switching and viewport-type menus have one honest graph-editor read

Important rule:
- `5.0E` is still pre-workspace cleanup
- it should not absorb the real pane-hosting and viewport-switching implementation from `[5.1]`

### Still Needed Decisions

#### `5.0.Q1` - What should happen to `Preview Mode` in the first cleanup pass?

Still needs decision:
- whether `Preview Mode` stays visible as a full left-dock card, becomes compact shell UI, or is hidden behind lighter access

Suggested answer:
- do not keep `Preview Mode` as a large always-open card
- reduce it to a compact control row or lighter entry surface
- preserve the still-needed mode-switch behavior, but stop spending full panel height on it
- safer removal order:
  - make `spaghetti` the default startup mode first
  - then remove the visible branch UI
  - then clean up legacy-only leftovers

#### `5.0.Q2` - What is the immediate direction for `Parts List`?

Still needs decision:
- whether `Parts List` should be merged into `Browser`, become a later hosted tool surface, or stay as a reduced temporary panel

Suggested answer:
- do not keep `Parts List` visible in the left dock
- treat it as one of:
  - near-term `Browser` merge candidate
  - later hosted tool surface
  - hidden transitional behavior while its long-range home is decided
- for `5.0`, the key outcome is removing the `Parts List` card from the left dock and naming its future direction explicitly

#### `5.0.Q3` - How aggressive should `Box Params` cleanup be?

Still needs decision:
- whether `Box Params` should be removed now, hidden by default, or only compacted while legacy workflows still depend on it

Suggested answer:
- do not do blind destructive removal in `5.0`
- hide `Box Params` from the left dock entirely
- if `Box Params` still supports a live needed workflow, preserve that behavior somewhere lighter instead of leaving it as a large always-open card
- if it is no longer central, phase it down from the default shell immediately

#### `5.0.Q4` - What behavior must be preserved during cleanup?

Still needs decision:
- how much of the current panel behavior must survive even if the shell cards themselves shrink or disappear

Suggested answer:
- preserve still-needed behavior first
- reduce surface size and default visibility before deleting real capability
- prefer:
  - compact row
  - hidden-by-default panel
  - menu entry
  - Browser merge
  - later hosted surface
- avoid deleting behavior just because the shell card looks legacy

#### `5.0.Q5` - How tightly should `5.0` couple to `[5.1] Workspace Modes`?

Still needs decision:
- whether `5.0` should only reduce clutter or also start implementing parts of the hybrid workspace system

Suggested answer:
- keep `5.0` narrow
- it should reduce shell clutter and unblock the left dock
- it should not absorb pane-tree, tiled hosting, divider authoring, or workspace persistence work from `[5.1]`

Plain-English rule:
- `5.0` simplifies the current shell
- `[5.1]` replaces the shell model

#### `5.0.Q6` - Should `5.0` include actual code removal for the legacy input path?

Still needs decision:
- whether `5.0` stops at hiding legacy-facing shell UI or also includes a later cleanup cut that removes `legacy` input branching from code

Suggested answer:
- yes, but as a later `5.0C` cleanup step
- first:
  - make `spaghetti` the default startup path
  - remove the visible branch UI
  - hide the left-dock legacy panels
- then:
  - remove the `legacy` input-mode branch from code explicitly as its own cleanup pass

Why:
- UI removal and code-path removal are different risk levels
- splitting them keeps the cleanup safer and easier to verify

### Acceptance Shape

`5.0` is done when:
- the left dock no longer feels dominated by `Preview Mode`, `Parts List`, and `Box Params`
- `Browser` reads as the primary left-dock surface again
- every reduced panel has a clear status:
  - kept but compacted
  - moved behind lighter access
  - merged into another surface
  - or explicitly phased down
- both `Preview Mode` and `Parts List` are hidden from the default left-dock stack
- `Box Params` is also hidden from the default left-dock stack
- the lane has an explicit later subphase for deleting the `legacy` input path from code instead of leaving that cleanup ambiguous
- no broad destructive legacy purge was required to get there
