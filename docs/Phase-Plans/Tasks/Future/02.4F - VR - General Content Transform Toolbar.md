## Doc Body

### Summary

Generalize the shipped reference transform toolbar into a broader viewer-side `Content` transform toolbar.

The intended direction is:
- one floating transform toolbar pattern
- one viewer-side gizmo/session system
- multiple eligible `Content` object types
- no confusion with source-authoring or Replicad-owned transforms

### Current Direction

- the existing reference transform toolbar is the first shipped proof surface
- the next step is to widen the target model from `reference only` to `eligible content object`
- Browser selection and/or Browser row actions should be able to enter the same transform session for any supported content item
- transforms stay viewer/runtime owned unless a later dedicated phase says otherwise

### First Likely Goals

- replace `reference transform session` language with a generic `content transform session`
- target by a generic content item identity instead of only `referenceId`
- keep the current toolbar/gizmo interaction model where possible
- preserve clear rules for:
  - open toolbar
  - activate `Move / Rotate / Scale`
  - keyboard shortcuts
  - camera lock
  - session-only overrides

### Open Questions

#### `2.4F.Q1` - First eligible object types

Still needs decision:
- which `Content` object types are eligible in the first general-content pass beyond references

Suggested answer:
- start with viewer-owned content that already behaves like scene instances
- do not include Replicad/source-authored geometry until a later explicit phase says so

#### `2.4F.Q2` - Entry behavior from Browser selection

Still needs decision:
- whether plain Browser row selection plus `m/r/s` should open the shared transform toolbar for eligible content items, or whether right-click/context action remains the only first entry path

Suggested answer:
- allow Browser-selected keyboard entry for eligible content rows once the generic session exists

#### `2.4F.Q3` - Persistence model

Still needs decision:
- whether generalized content transform overrides remain workspace-session-only in the first pass or whether some content classes persist those transforms

Suggested answer:
- keep the first generalized pass workspace-session-only for consistency with the current reference transform system

#### `2.4F.Q4` - Capability matrix per content type

Still needs decision:
- whether every eligible content type gets the full `Move / Rotate / Scale` set, or whether capabilities vary by object type

Suggested answer:
- allow a per-type capability matrix so unsupported transform modes can be hidden or disabled cleanly

#### `2.4F.Q5` - Toolbar naming and ownership

Still needs decision:
- whether the current `ReferenceTransformToolbar` should be evolved in place or replaced by a more generic `ContentTransformToolbar`

Suggested answer:
- rename toward a generic content transform surface once the target model truly widens beyond references
