## Arch Spec

### Spec Target

This implementation target is only:
- `[1.2C] GE - Phase 11C - Save/Load Interaction With Editors`

This cut is intentionally narrow:
- define how a graph is opened into an editor
- define when a new editor should open versus when the current editor should swap
- define `Load Into New Graph` behavior
- keep raw file IO and Browser cached lifecycle below this layer

If this cut is wrong, later work has no stable base for:
- clean Browser/editor coordination
- predictable editor graph switching
- project-file ownership above multiple live cached graphs

### Problem Statement

After `11A` and the planned `11B`, the app can have:
- durable graph-document files
- Browser-owned cached graph entries

But it still does not have:
- explicit editor-facing load/open actions
- a decision for when to reuse an editor viewport versus create a new one
- a decision for when loaded content becomes a new graph copy versus replaces the current editor target

Current runtime still behaves too much like:
- Browser and editor relationships are implied by focus/open state
- load/open actions would be forced to guess between replace, copy, or open-new behavior
- identity and editor-binding rules would be easy to blur

`11C` needs to make those editor-facing actions explicit before `GE 12` deepens project-level ownership.

### Locked Direction

- `11C` owns editor-facing save/load interaction policy
- `11C` builds on the shipped `11A` persistence seam
- `11C` builds on the planned `11B` cached-graph layer
- Browser cached entries remain Browser-owned
- editor viewports remain viewport-owned surfaces that bind to graph/cached entries through explicit actions

### First-Pass Editor Interaction Direction

Use this first-pass direction:

```ts
type EditorLoadAction =
  | 'openGraph'
  | 'loadIntoNewGraph'
  | 'openInNewEditor'
  | 'swapCurrentEditor'
```

Rules:
- `Open Graph` should use an existing cached graph entry
- `Load Into New Graph` should create a new live graph copy suitable for editing
- `Open In New Editor` should open another viewport bound to the chosen graph/cached entry
- `Swap Current Editor` should rebind the focused viewport instead of opening a new one
- `11C` may keep the first implementation narrow as long as these actions are explicitly separated

### Locked Editor Coordination Rules

- Browser chooses the target graph/cached entry
- editor actions decide how that target binds to one or more viewports
- viewport identity is not graph identity
- cached-entry identity is not viewport identity
- copy/import behavior should avoid silent identity collisions
