### Spec Target

- `[3.1] NI - Node System Cleanup And Growth`

- after Lane `[2]` Browser/content structure work is honest enough to support later authoring growth
- before the more specific foundational geometry-node work in `[3.2]`

### Problem Statement

The node system currently carries too much ambiguity in:
- node-family boundaries
- generic versus one-off rendering rules
- palette/spawn expectations
- how future composite and feature nodes are supposed to fit into the registry/template model

If `[3.1]` is skipped or stays too vague:
- `[3.2]` may force special cases into the node system
- later geometry-node growth may hard-code product-specific assumptions
- palette, rendering, and node-shell inconsistencies may become harder to unwind

### Locked First-Pass Win

`[3.1]` counts as real when:
- the generic node framework is clearer than it is today
- node-family boundaries are easier to explain
- node rendering contracts are strong enough for the coming geometry-node work
- the palette/spawn model is no longer an obvious blocker to node growth

Plain-English rule:
- make the node framework worthy of the richer geometry nodes before those nodes carry more weight

### Planned Work Buckets

#### 1. Node Family Boundaries

- clarify the intended difference between:
  - param/value nodes
  - primitive/source nodes
  - operation nodes
  - composite nodes
  - output/system nodes

#### 2. Registry And Ownership Rules

- define what belongs in:
  - node registry metadata
  - schema/type definitions
  - node-render templates
  - editor-only view helpers

#### 3. Palette / Spawn Cleanup

- define how nodes should be surfaced and spawned without hard-coding product-specific paths
- keep future geometry nodes compatible with one general spawn model

#### 4. Generic Node Rendering Contracts

- define the shared node-shell behavior future nodes should inherit
- keep future `Sketch`, `Extrude`, and `Loft` from having to invent bespoke shells for basic authoring needs
