## Doc Body

### Summary

Extend the shipped console shell so it becomes the real command-input seam for the app instead of only a narrow transcript surface.

`4.1C` is locked as:
- explicit console text-entry mode via `click/focus` or `/`
- narrow-core first shipped command set
- strict command parsing with simple aliases only
- `Up / Down` history recall while the console input is focused
- immediate `M / R / S` hotkeys outside text-entry mode
- `X / Y / Z` only as secondary transform-chain modifiers
- standalone `Z` reserved for zoom selected
- `Esc` cancels the currently active command/session, not committed work

### Locked Outcome

`4.1C` should deliver:
- real typed command submission beyond the current narrow console seam
- real command history recall in the console input
- explicit keyboard ownership rules between:
  - normal app mode
  - console text-entry mode
  - existing text fields elsewhere
- a first locked shortcut split between:
  - immediate transform-start hotkeys
  - secondary transform-axis modifiers
  - typed command aliases inside text-entry mode

### Command Entry Rules

The first shipped `4.1C` entry rules are:

- `click/focus` always enters console text-entry mode
- `/` also focuses the console input as the first keyboard entry shortcut
- printable typing should not be globally captured unless the console is explicitly focused
- normal `input`, `textarea`, `select`, and contenteditable surfaces keep keyboard ownership

Important rule:
- the console must not steal typing from any existing real text-editing field
- `/` is the only first-pass keyboard entry shortcut for focusing the console input

### Keyboard Ownership Rules

The implementation should treat keyboard behavior as three states:

- normal app mode
  - immediate app/tool hotkeys still work
  - printable typing does not go to the console unless the console is explicitly focused

- explicit console text-entry mode
  - printable typing goes into the console input
  - `Enter` submits the current command text
  - `Up / Down` navigates command history
  - immediate app-level tool hotkeys do not fire while the console input owns text entry

- existing text-field ownership mode
  - normal `input`, `textarea`, `select`, and contenteditable surfaces keep the keyboard
  - the console router must ignore those fields

### Hotkey Split

The first-pass shortcut split is locked as:

- immediate standalone hotkeys outside console text-entry mode
  - `M`
  - `R`
  - `S`
  - standalone `Z` for zoom selected / zoom object

- secondary transform-chain modifiers only
  - `X`
  - `Y`
  - `Z`
  - these only make sense after an active transform chain already exists, for example:
    - `M > X`
    - `M > Y`
    - `M > Z`
    - `R > X`
    - `R > Y`
    - `R > Z`
    - `S > X`
    - `S > Y`
    - `S > Z`

Important rules:
- `X / Y / Z` must not start transform commands by themselves outside an active `M / R / S` chain
- standalone `Z` must remain reserved for zoom selected instead of being consumed as a transform-axis shortcut
- the console transcript should still reflect immediate hotkey actions even when they are not typed into the console input

### Parsing And History Rules

The first parser/history behavior is locked as:

- strict command-name matching
- only obvious simple aliases where intentionally listed
- no fuzzy matching
- no broad partial matching
- `Up / Down` navigates command history while the console input is focused
- no heavy history UI is required in `4.1C`

### First Shipped Command Set

The first shipped `4.1C` command set is locked as `Narrow Core`:

- core console
  - `help`
  - `console`
  - `clear`
  - `history`

- view / selection
  - `frame`
  - `zoom`

- transforms
  - `move`
  - `rotate`
  - `scale`
  - `snap`

- debug / runtime
  - `echo`
  - `status`

Simple first-pass aliases may exist, but only inside explicit text-entry mode:
- `move` / `m`
- `rotate` / `r`
- `scale` / `s`
- `zoom` / `z`

Important rule:
- typed aliases inside text-entry mode must not replace the existing immediate hotkeys outside text-entry mode

### Escape And Cancel Rules

`Esc` is locked as a cancel key for the currently active command/session, not as an undo for already-committed work.

If a live transform command is active:
- `Esc` stops that command immediately
- restores the pre-command baseline
- clears the active command/session state

If no live command is active and the user is only in console text-entry mode:
- first `Esc` clears unsubmitted input text
- second `Esc` exits console text-entry mode if the field is already empty

If nothing is active and there is no console text-entry state to clear:
- `Esc` does nothing

### Important Interfaces / Behavior To Lock

- console input modes:
  - normal app mode
  - explicit console text-entry mode
  - existing-text-field ownership mode
- command/history behavior:
  - strict parsing
  - `Up / Down` history recall in focused console input
  - `Enter` submits typed command text
- shortcut ownership:
  - immediate standalone transform-start hotkeys
  - secondary transform-axis modifiers only after active transform start
  - standalone `Z` remains zoom selected
- escape behavior:
  - cancel active command/session first
  - clear text-entry state second

### First-Pass Integration Shape

`4.1C` should extend the already-shipped console shell and window modes instead of rebuilding them.

The implementation should stay centered around:
- the existing `src/app/console/` store and shell components
- app-shell level keyboard routing
- feature areas that already emit shortcut-like behavior
- the current console transcript/log seam

Likely implementation seams:
- `src/app/console/`
- `src/app/AppShell.tsx`
- `src/app/store/`
- `src/app/theme/v15Theme.css`
- feature areas that currently emit shortcut or command-like events

### Locked Deferrals

Keep these out of `4.1C`:

- fuzzy command parsing
- autocomplete
- broad command-language expansion
- hotkey rebinding UI
- transcript persistence/export
- replacing the debug inspector

Those belong in later `4.1D+` work.
