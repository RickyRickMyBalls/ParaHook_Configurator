### Purpose

This file is the execution spec for:
- `[2.1E] VR / SP - Dockable Left Panels And In-App Floating Panel Shell`

Use it to:
- replace Browser-only dock/floating follow-ups with one reusable left-dock shell system
- let the docked `Browser` and docked `meatball editor` share one drag-out and drag-back docking contract
- make dragging the docked `meatball editor` out of the left dock restore the normal floating `Spaghetti Editor` presentation instead of creating a separate floating meatball shell
- lock the ghost-preview and dock-target behavior before implementation starts

## Scope

This phase covers:
- one reusable in-app dockable left-panel shell for:
  - `Browser`
  - `meatball editor`
- explicit docked versus floating presentation state for those two panel types
- drag-out from the docked titlebar into a floating in-app window
- drag-back from the floating window into a valid left-dock target
- compact ghost-preview placeholders that appear over valid dock targets
- push-down animation of downstream left-dock content while the preview is active

This phase does not cover:
- detached/new-browser windows
- arbitrary panel reordering inside the left dock
- turning `Preview Mode` or `Parts List` into movable floating panels
- broader generic workspace-presentation systems outside the left dock
- changes to `2.1D` editor window-mode rules such as split, maximize, or full floating editor behavior

Working scope rule:
- `2.1E` should finish the shared left-dock dock/floating shell behavior for the first two supported panel types without turning into a full generic movable-panel framework

## Arch Spec

### Spec Target

This implementation target is only:
- `[2.1E] VR / SP - Dockable Left Panels And In-App Floating Panel Shell`

This cut intentionally sits:
- after the first shipped Browser popout/floating work
- alongside the still-open `2.1C` Browser cleanup work
- after the active `2.1D` Spaghetti shell/view-mode wave establishes the docked `meatball editor` host
- before any later fully generic movable-panel system

### Problem Statement

The app already has the beginnings of two separate left-panel shell stories:
- `Browser` can dock and float
- `meatball editor view` can dock below `Parts List`

But the current shell is still too one-off because:
- Browser floating logic is ad hoc and panel-specific inside `AppShell`
- Browser re-docking does not yet share a reusable dock-target contract
- the docked meatball host is not yet able to drag out and restore the normal floating `Spaghetti Editor`
- there is no shared ghost-preview or dock-slot animation model across dockable left panels

`2.1E` needs to turn that into one reusable left-dock shell contract without pulling every other left-dock panel into the same phase.

### Locked Current-State Framing

This spec assumes:
- `Browser` already has a blue titlebar and a first in-app floating mode
- `Browser` already supports explicit popout and docked-titlebar drag-out
- `meatball editor view` already exists as a docked editor host below `Parts List`
- `AppShell` already owns the main left-dock layout and the floating shell overlays

This doc does not describe:
- detached browser/OS windows as shipped behavior
- arbitrary left-dock panel rearrangement
- multiple Browser instances

### Locked Panel Scope

Supported dockable left panels in `2.1E`:
- `browser`
- `meatball-editor`

Explicitly deferred:
- `Preview Mode`
- `Parts List`
- other future left-dock utilities

Rule:
- build one reusable system now
- only wire the first two panel types in this phase

### Locked Shared Shell State Contract

`AppShell` should own a shared local panel-shell model with:
- `DockableLeftPanelId = 'browser' | 'meatball-editor'`

Per-panel shell state should include:
- `isFloating: boolean`
- `isCollapsed: boolean`
- `position: { x: number; y: number }`
- `size: { width: number; height: number }`

Rules:
- Browser collapse remains shell-local UI state under this model
- meatball editor collapse continues to mean the existing editor-shell collapsed presentation when applicable
- editor viewport/window-mode ownership stays in spaghetti/editor state
- the left-panel docking shell only controls panel presentation, dragging, and docking

### Locked Dock Target Contract

Dock targets are fixed slot targets, not freeform anywhere-in-dock insertion.

In `2.1E`:
- `browser` docks only to the Browser slot at the top of `.PanelStack`
- `meatball-editor` docks only to the meatball slot below `Parts List`

Rule:
- a floating panel can only preview and dock into its own assigned target
- no cross-docking between Browser and meatball

### Locked Drag-Out Behavior

From docked state:
- pressing and dragging the blue titlebar starts a possible undock gesture
- once the pointer passes the undock threshold, the panel becomes floating
- the new floating window seeds from the real docked rect
- the drag continues seamlessly without a second click

This should work for:
- `Browser`
- docked `meatball editor`

Meatball-specific drag-out rule:
- dragging the docked `meatball editor` out of the left dock should immediately restore the normal floating `Spaghetti Editor`
- there is no separate floating `meatball editor` shell state
- `meatball editor` remains the docked toolbar-hosted presentation only

### Locked Drag-Back / Ghost Preview Behavior

While a supported floating panel is being dragged:
- test pointer overlap against that panel's fixed dock target
- when the pointer enters the valid dock target, show a compact ghost preview placeholder
- animate the downstream dock content downward while the preview is visible
- clear the preview immediately when the pointer leaves the valid target

Ghost preview styling must be:
- compact row/panel-entry height
- white translucent fill
- dashed white border
- symbolic only, not a live panel clone

### Locked Drop Behavior

On pointer release while dragging a floating left panel:

If dock preview is active:
- re-dock that panel into its fixed target
- clear floating drag state
- clear ghost-preview state
- preserve the panel's collapsed state

If dock preview is not active:
- keep the panel floating
- clear drag state only

### Locked Meatball-Specific Behavior

Dragging the docked meatball titlebar should:
- exit the docked `meatball editor` presentation
- restore the normal floating `Spaghetti Editor`
- continue the same drag seamlessly on that floating editor shell

Dragging the floating meatball back to its valid dock target should:
- re-enter `meatball editor view`
- re-dock it below `Parts List`

Rules:
- `meatball editor view` remains a real editor presentation mode
- `2.1E` must not redefine meatball as a generic left utility panel
- `2.1D` still owns the editor mode transitions that place a viewport into `meatball editor view`
- the only floating editor shell remains the normal `Spaghetti Editor` shell

### Current Seam Findings

Current shell facts that this phase should reuse:
- `AppShell` already owns the left-dock layout and Browser floating overlay
- `AppShell` already has Browser drag refs, resize refs, and docked-host refs
- `BrowserPanel` already accepts reusable titlebar shell hooks:
  - `isFloating`
  - `onTogglePopout`
  - `onTitleBarPointerDown`
- the docked meatball host already renders under `Parts List` inside `.PanelStack`
- the current meatball host already reuses the Spaghetti titlebar/body shell

### Implementation Order

1. Promote the Browser-specific floating/docking state in `AppShell` into one shared left-panel shell model keyed by panel id.
2. Introduce fixed dock-target wrappers for the Browser slot and meatball slot inside the left dock.
3. Add shared floating-drag and dock-preview logic for supported left panels.
4. Render the compact ghost-preview placeholder and animate downstream left-dock content when a valid target is active.
5. Wire `Browser` onto the shared system without changing its existing popout/collapse behavior.
6. Wire the docked `meatball editor` host onto the same shared system so its titlebar can drag out by restoring the normal floating `Spaghetti Editor` shell and drag back into its dock slot by re-entering `meatball editor view`.
7. Keep split, maximized, and main floating-editor overlay behavior outside this phase.

## Assumptions And Defaults

- one `Browser` instance only
- one docked meatball host only
- dock targets are fixed slot targets rather than arbitrary reordering
- `Preview Mode` and `Parts List` remain docked-only
- no detached/new-browser windows are included
- ghost preview height should read like a normal panel-entry placeholder, not like a full panel replacement
