### Recommended Required Layers

Recommended required first-pass console layers:

- `Commands`
  - typed commands and command-like actions the user explicitly triggered
- `Shortcuts`
  - keyboard shortcut activity such as mode switches and transform hotkeys
- `App`
  - high-level app/system notes
- `Worker`
  - build/runtime/worker messages
- `Diagnostics`
  - warnings, failures, and errors
- `Params`
  - slider/value/transform/snap changes
- `Selection`
  - active selection and target changes

Good later follow-up layers:

- `View`
  - camera/frame/lock/view-mode notes
- `Browser`
  - Browser row actions and object import/remove events
- `Transforms`
  - gizmo and transform-session-specific messages
- `Timeline`
  - timeline mode, playback, and evaluation notes

### Open Questions

#### `4.1.Q1` - First pass input scope

Still needs decision:
- whether the first shipped console should already accept typed command input, or whether it should start as a feedback/transcript surface with minimal or placeholder input behavior

Suggested answer:
- allow the collapsed row to own the future input seam, but keep the first pass focused on command/shortcut/debug feedback if that gets the console shipped faster

#### `4.1.Q1A` - Immediate hotkeys vs typed command entry

Still needs decision:
- whether single-key commands like `M`, `R`, and `S` should require `Enter` once the console exists, especially if longer text commands like `mirror` also need to be supported

Suggested answer:
- reserved single-key tool hotkeys should execute immediately without `Enter`
- longer typed commands should only begin when the user explicitly enters console text-entry mode
- that means:
  - plain `M`, `R`, `S`, `X`, `Y`, `Z` can remain fast command/hotkey actions
  - typed commands like `mirror` should require focused console text-entry mode plus `Enter`
- this keeps high-frequency tool flow fast while avoiding collisions between hotkeys and longer command names

#### `4.1.Q1B` - User hotkey customization

Still needs decision:
- how much of the shortcut system should be user-customizable in the first honest console/hotkey pass

Suggested answer:
- the system should be designed so user hotkey customization is possible
- but the first console implementation does not need to ship full rebinding UI if that would slow down the shell/transcript cut too much
- the later hotkey-customization surface should include:
  - rebinding for command and tool shortcuts
  - conflict detection
  - restore-default behavior
  - clear separation between reserved text-entry behavior and rebindable tool shortcuts

#### `4.1.Q2` - Expansion behavior

Still needs decision:
- whether the first expanded console should open as a bottom-docked panel, a floating panel, or support both modes immediately

Suggested answer:
- start with a bottom-docked expanded panel so the first implementation stays structurally simple and shell-owned

#### `4.1.Q3` - Layer filtering controls

Still needs decision:
- how much per-layer filtering UI is needed in the first cut

Suggested answer:
- first pass should at least let the user see distinct layers and probably toggle them, but should avoid a heavy inspector-like control surface

#### `4.1.Q4` - Console vs Debug Inspector relationship

Still needs decision:
- what debug information should move into the console now versus stay in the existing read-only debug inspector

Suggested answer:
- use the console for chronological command/event/status text
- keep structured deep inspection in the existing debug inspector for now

#### `4.1.Q5` - Initial ownership seams

Still needs decision:
- which store and shell seams should own the first console state, transcript entries, and expansion mode

Suggested answer:
- keep one app-global console store and one shell-owned placement seam, then let feature areas push messages into it through narrow append/log helpers
