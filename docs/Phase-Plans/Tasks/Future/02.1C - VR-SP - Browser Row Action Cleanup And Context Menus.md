### Problem Statement

The Browser is structurally honest enough after `2.1A` and `2.1B`:
- graph rows exist
- published-output rows exist
- viewport/session rows exist
- selection is Browser-local
- editor and viewer actions are explicit

But the Browser still needs a completion pass because:
- row cleanup is only partially landed
- right-click exists, but the final discoverability model is not locked yet
- `Open Viewports` reads more literally than the current shell behavior actually supports
- the Browser still needs one explicit rule for what its editor-surface branch means now versus what it will mean later

`2.1C` needs to finish that cleanup without reopening deeper hierarchy work or prematurely implementing true multi-window editing.

### Locked Current-State Framing

This spec assumes:
- `2.1A` already shipped the shared Browser row shell
- `2.1B` already shipped Browser/editor/shared-viewer coordination
- the repo already shipped a first `2.1C` slice that:
  - removed visible row button strips
  - added right-click context menus

This doc does not describe `2.1C` as a blank-slate phase.

Plain-English rule:
- `2.1C` is already started; this spec locks what still has to happen before the Browser cleanup is actually complete

### Locked Naming Rule

The Browser should rename:
- `Open Viewports`

to:
- `Open Editors`

Meaning in the current shell:
- this branch currently lists editor viewport/session records
- it does not yet guarantee that every listed entry is a separately visible floating editor window at the same time

Future meaning:
- this same branch remains the Browser home for all open editor surfaces later, including:
  - in-app floating editor windows
  - detached/separate editor windows if they land later

Why this cut is right:
- `Open Editors` is more honest than `Open Viewports` today
- it still preserves the intended future branch identity instead of forcing a temporary overly-technical label

### Locked Command Access Rule

The final `2.1C` command model is:
- `right-click + small ... overflow`

Rules:
- right-click remains supported on graph, published-output, and editor-session rows
- a small `...` overflow affordance should be added for discoverability
- the overflow affordance is not a return to visible row button strips
- right-click and overflow should expose the same row action list and use the same action-running path

Why this cut is right:
- right-click keeps the Fusion-style tree cleaner
- `...` keeps the command surface discoverable for users who do not naturally rely on context menus

### Locked Row Anatomy

Rows should read primarily as:
- `[Chevron] [Type/State Icon Cluster] [Label] [Quiet Meta] [Optional ...]`

Working rules:
- the tree remains visually primary
- rows stay selection-first
- heavy commands stay off the default row face
- the overflow trigger is:
  - small
  - quiet
  - clearly secondary to the hierarchy and label

The row should not return to:
- visible `Save / Open / Reveal / New Editor / Swap Editor / Focus / Close` button strips

### Locked Browser Honesty Rule

`Open Editors` must read honestly relative to the current shell:
- the Browser may list editor viewport/session entries
- it must not imply that the shell already renders multiple visible spaghetti editor windows when it still mostly renders one active floating editor surface

That means:
- row labels and section labels should stay human-readable
- Browser meta should describe current editor/focus state without pretending that true multi-window shell behavior has already landed
- this phase may improve wording and row meta presentation, but it must not fake `SP - Phase 13`

Plain-English rule:
- the Browser can track future editor surfaces now, but it should not claim that later shell behavior already exists

### Current Seam Findings

- already owns the Browser row rendering surface
- already has right-click context-menu state from the first landed `2.1C` slice
- is the correct place to:
  - rename `Open Viewports` to `Open Editors`
  - add the small `...` overflow trigger
  - keep row selection and command access unified

  - graph-document rows
  - published-output rows
  - editor-session rows
- should continue to be the single row-action metadata surface used by both right-click and overflow

- already centralizes action execution across row kinds
- should remain the one runner for both context-menu and overflow-triggered commands

`AppShell.tsx`
- still renders only `selectActiveEditorViewport`
- is the proof that current shell behavior remains:
  - one active floating editor surface
  - not literal multi-window rendering yet

### Implementation Order

1. Rename the Browser branch from `Open Viewports` to `Open Editors`.
2. Add a small `...` overflow affordance to graph, published-output, and editor-session rows that have row actions.
3. Route the overflow affordance through the same action metadata and action runner already used by right-click.
4. Normalize row meta/state copy so the Browser reads as calm editor-session tracking rather than over-claiming literal multi-window UI.
5. Keep the Browser selection-first and tree-first throughout the cleanup.
6. Stop before any shell change that would render multiple floating editor windows at once.

### Deferred / Out Of Scope

- any shell rewrite that renders all editor viewport records simultaneously
