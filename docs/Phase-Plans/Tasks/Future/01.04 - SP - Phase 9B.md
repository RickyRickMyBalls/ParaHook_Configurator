## Arch Spec

### Spec Target

This implementation target is only:
- `[1.1B] SP - Phase 9B - Multi-Editor Browser Foundation`

This cut is intentionally about coordination above the graph-document core:
- allow more than one graph editor surface to exist
- let Browser reflect and manage open/focused editor viewports
- let one viewport switch which graph it is showing
- stop treating spaghetti as one app-wide mode/panel

If this cut is wrong, later work has no stable base for:
- Browser graph navigation
- focused/open editor management
- graph switching across viewports
- later project-level content ownership

### Carry-Forward From `9A`

Locked carry-forward rules from `9A.1` through `9A.3`:

- `useSpaghettiStore` remains the right home for graph + viewport runtime state
- `useAppStore` should stay shell/bridge-oriented
- graph-owned truth must stay graph-owned
- local presentation state should not drift into graph truth
- narrow temporary bridges are acceptable if they stay explicit and small

Working read:
- `9B` should build on `9A.3`, not re-decide `9A.3`
- this phase expands the viewport system, not the graph-document contract

### Problem Statement

After `9A.3`, the app has:
- explicit graph documents
- graph-owned authored canvas truth
- the first explicit editor viewport seam

But it still does not have:
- more than one live editor viewport
- Browser-coordinated viewport focus/open state
- graph switching inside one viewport
- a true replacement for the old one-window spaghetti assumption

Current runtime still behaves too much like:
- one floating spaghetti surface
- one active spaghetti mode
- one panel/editor stack that happens to be viewport-bound

`9B` needs to make the viewport system real without pulling in graph-local build routing or project/file ownership.

### Locked Direction

- the spaghetti editor is a viewport into a graph document, not the owner of graph truth
- Browser coordinates viewport records, not graph truth
- spaghetti must stop being one app-wide mode/panel

### Browser Surface Direction

Visual direction for the Browser:

- the Browser should read like a Fusion360-style left hierarchy tree
- it should be a docked left-side tree/navigation surface, not a floating inspector
- the first useful mental model is:
  - expandable hierarchy rows
  - open / focus / visibility style controls on rows
  - graph/document entries that can expand into deeper content later

What this means for `9B`:

- Browser should already feel like a hierarchy tree, even if the first pass is still simple
- the `9B` implementation does not need final polish, but it should not be shaped like a flat list or temporary debug panel
- future additions such as loading bars and richer row-level controls should fit under tree rows instead of requiring a different Browser layout later

### Locked Runtime Placement

- viewport records stay in `useSpaghettiStore`
- Browser coordinates viewport records, not graph truth
- `useAppStore` remains app-shell mode state plus current compile/build bridge behavior
- `AppShell` becomes a viewport renderer/host, not the owner of the only spaghetti window

### Locked Viewport Model

Use this first-pass `9B` runtime model:

```ts
type EditorViewport = {
  editorViewportId: string
  graphDocumentId: string
  isFocused: boolean
  windowMode: 'collapsed' | 'meatball editor view' | 'expanded' | 'separateWindow'
  position: { x: number; y: number }
  size: { width: number; height: number }
  zOrder: number
}
```

Rules:
- multiple editor viewports may exist
- one focused viewport exists
- one `meatball editor view` exists at most
- viewport state owns:
  - graph binding
  - window mode
  - focus
  - position
  - size
  - z-order
  - local viewport presentation state
- graph state does not absorb any of that

### Locked Focus Rules

- focus follows the last editor viewport the user clicked in
- hover does not change focus
- the focused viewport rises in z-order
- Browser reflects focused/open viewport state
- keyboard commands and viewport-scoped actions route to the focused viewport

### Locked Interaction Rules

- graph switching inside one editor viewport happens through the graph-name dropdown in the editor header
- the first item in the editor header should be the focused graph name
- selecting a graph from that dropdown switches what that viewport is showing
- graph switching does not move graph ownership into the viewport
- Browser is the viewport manager and project navigation surface
- Browser does not own graph nodes, edges, params, or compile/build truth

### Browser / Viewport / Editor Flow

Lock this first real `9B` flow:

- Browser owns the list of open editor viewports
- Browser can focus an existing viewport
- Browser can open a graph in a viewport
- focused viewport drives keyboard/viewport-scoped actions
- `AppShell` renders a viewport list or focused stack instead of one implicit spaghetti window
- `SpaghettiPanel` and `SpaghettiEditor` consume explicit viewport identity
- editor header graph dropdown switches `graphDocumentId` for that viewport

Working implementation consequence:
- `9B` should expand the current `activeEditorViewportId` seam into a true open/focused viewport collection
- `9B` should not move graph ownership out of the graph-document layer

### First `9B` Implementation Preference

Lock this implementation preference:

- start with the Browser-managed open/focus model first
- keep only one visible floating spaghetti surface in the first `9B` implementation pass
- treat that as the structural first step
- add true multiple visible windows later once the Browser/open/focus foundation is real

Why this is the right first cut:

- Browser/open/focus structure is the more important architectural element
- it reduces the chance of mixing Browser coordination work with multi-window polish too early
- it still moves the app away from the old one-window spaghetti assumption in a controlled way

### Viewport-Owned Vs Graph-Owned

#### Graph-owned in `9B`

# Close Out notes

- The biggest real `9B` seam was not the visible Browser tree. It was the hidden bridge bug that viewport focus/document switching did not refresh the canonical active `graph` cache and derived part-cache state. `9B` forced that bridge to become real, which was necessary so compile/build could keep following the focused viewport without pulling `9C` forward.
- The Browser-first implementation preference was the right call. A permanent left docked Browser tree plus one focused floating surface landed the structural open/focus model without collapsing into full multi-window management too early.
- The follow-up startup fix mattered: seeding a default open spaghetti viewport caused the viewer to fall into an empty graph path too easily. The better first-pass `9B` behavior is Browser-first with no auto-open viewport on boot, while the legacy viewer stays visible until a real graph viewport is explicitly opened.
- The first project-style Browser tree should stay understood as a UI shell backed by current graph/viewport runtime, not as true project ownership. That boundary kept `9B` from drifting into `GE 12`.
- `inputMode` is still a temporary shell gate for showing/hiding the floating spaghetti surface, but it is no longer the real owner of which graph/editor is active. Browser/open-focus state now carries that structural responsibility.
- The next real pressure seam is `9C`, not more Browser polish. `9C` should now focus on graph-local compile/build/preview-prep memory while Browser/viewports keep owning only navigation, focus, geometry, and local presentation behavior.
