## Doc Body

### Summary

`5.0D` is the catch-all cleanup cut for everything that is still left in after the real `5.0A-C` work lands.

This phase exists so ParaHook can:
- remove dead shell residue without pretending it blocks `[5.1]`
- separate `required spaghetti-first cleanup` from `nice-to-have post-cleanup pruning`
- make explicit decisions about whether old viewer/panel concepts still deserve to exist

Important rule:
- `5.0D` is deferred cleanup
- it should not hold up the main `[5.1] Workspace Modes` lane unless one of these leftovers turns out to be a direct blocker

### Locked Outcome

At the end of `5.0D`:
- obviously dead shell surfaces and panel files are removed
- stale tests, CSS, and imports from removed surfaces are cleaned up
- any surviving viewer concepts such as `parts` versus `assembled` are either:
  - explicitly kept as real product behavior
  - or removed with a named replacement path
- the app no longer carries ambiguous "maybe legacy, maybe still real" residue from the old left-dock era

### Still Needed Decisions

#### `5.0D.Q1` - Should `Toolbar.tsx`, `PartsListPanel.tsx`, and `BoxPanel.tsx` be removed entirely once they leave the shell?

Suggested answer:
- yes, unless one of them is being deliberately repurposed into a real later hosted surface
- dead shell surfaces should not remain in the repo just because they were recently removed from `AppShell`

#### `5.0D.Q2` - Is `parts` versus `assembled` still a real ParaHook viewer concept after `5.0C`?

Suggested answer:
- treat this as an explicit product decision, not as accidental residue
- if `parts` versus `assembled` still matters to the user, keep it and give it a real home
- if it was mainly tied to the removed preview/legacy panel flow, remove it here

#### `5.0D.Q3` - Does `Spaghetti Editor` depend on `PartsListPanel` as a UI surface?

Suggested answer:
- no
- the editor and graph authoring flow should not depend on the old `PartsListPanel` card existing
- only keep spaghetti-side output-list logic if it still supports a real future surface or workflow

#### `5.0D.Q4` - Should leftover spaghetti output-list selectors be kept even if the old panel disappears?

Suggested answer:
- keep them only if they have a clear next owner:
  - `Browser`
  - a later hosted output surface
  - a real viewer/output inspector
- otherwise remove them with the dead panel cleanup

#### `5.0D.Q5` - Does `5.0D` block `[5.1] Workspace Modes`?

Suggested answer:
- no, by default
- `5.0D` is intentionally deferred so workspace-mode work does not wait on every last dead file cleanup
- only promote an item from `5.0D` into the critical path if it becomes a direct blocker for `5.1`

### Acceptance And Done Shape

`5.0D` is done when:
- the dead shell-panel files left behind after `5.0A-C` are either removed or explicitly re-homed
- stale CSS, tests, and imports from removed surfaces are cleaned up
- `parts` versus `assembled` has an explicit keep-or-remove decision
- spaghetti-side output-list helpers are either justified by a real owner or removed
- no ambiguous post-legacy residue remains just because it was inconvenient to classify during `5.0A-C`
