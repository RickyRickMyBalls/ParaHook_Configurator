### Spec Target

This implementation target is only:
- `[1.6] SP - Phase 12 - Shared Viewport Composition`

- after `SP - Phase 11`

- before `SP - Phase 13`

This phase stays single-phase for the first pass because the current locked cut is still one coherent seam:

- no detached multi-window or Browser-authoring expansion

### Problem Statement

The app now has:
- graph documents
- graph-local compile/build/output ownership
- project-above-graphs ownership
- a first Browser/project surface
- editor viewports bound to graph documents
- one shared viewer that currently resolves one graph-targeted preview path at a time

But it still does not have:
- one explicit shared viewport composition model
- a way for more than one editor viewport's graph document to intentionally participate in one shared viewer result
- composition truth that stays stable when focus changes
- visible membership behavior that proves the workspace is more than one implicit active graph plus one viewer target

Current viewer/runtime coordination still behaves too much like:
- one `viewerTargetGraphDocumentId`
- one graph-targeted preview/render path in the shared viewer
- focused viewport and active graph convenience state standing in for composition truth

`SP - Phase 12` needs to add one honest shared viewport composition seam before later multi-window editing and later debug/polish work can grow without reinforcing singleton viewer behavior.

### Locked Direction

- `SP - Phase 12` is a viewer/workspace coordination phase, not a project-ownership or Browser-content phase
- the first pass should let one shared viewer intentionally present contributions from more than one graph-backed workspace surface
- composition truth must be explicit and must not be inferred from:
  - `activeGraphDocumentId`
  - `viewerTargetGraphDocumentId`
  - focused editor viewport state
- the shared viewer remains a presentation surface and must not become the owner of graph or project truth
- composition authoring is explicit in the first pass
- the first pass remains narrow and visible rather than expanding into detached-window or Browser interaction systems

### Locked First-Pass Composition Unit

The first-pass composition unit is:
- graph documents

That means:
- shared composition membership is a set or ordered list of `graphDocumentId`s
- each participating graph contributes its current viewer-facing preview/renderable output path to the shared viewer

Do not use as first-pass composition units:
- published output entries
- project components
- object rows
- part rows

Why this cut is correct:
- it matches the current `viewerTargetGraphDocumentId` seam cleanly
- it keeps `SP - Phase 12` in viewer/workspace coordination rather than Browser/content semantics
- it avoids pulling this phase into later output-structure and project-content work

Plain-English rule:
- first compose whole graph contributions, not finer-grained content units

### Locked Authoring Entry Path

The first-pass authoring path is:
- explicit graph/editor viewport action

That action should let the user:
- add the viewport's bound graph document to the shared composition
- remove the viewport's bound graph document from the shared composition
- clearly see whether that viewport/graph is participating

Do not use as the first-pass primary authoring path:
- automatic participation from all open viewports
- Browser graph-row authoring
- detached-window authoring

Why this cut is correct:
- it keeps `SP - Phase 12` anchored to viewport/workspace behavior
- it avoids Browser interaction sprawl before later Browser phases
- it prevents composition membership from being inferred from focus or open-state alone

Plain-English rule:
- the user explicitly joins a viewport/graph to shared composition

### Locked Composition Truth Boundary

First-pass composition truth lives in:
- workspace/runtime-owned coordination state in `useSpaghettiStore`

It does not live in:
- graph-authored truth
- project-content truth
- Browser row state
- focused viewport convenience state

The first-pass composition state should explicitly carry:
- a shared composition or composition-session identity
- participating graph document ids
- shared viewer composition identity or active composition target
- optional explicit participation order if the implementation chooses to store it directly
- viewport actions stay the first authoring path, but viewport ids do not need to become persisted composition truth in the first pass

Focus state may:
- seed convenience actions
- help the UI decide which viewport action is currently in reach

Focus state must not:
- silently redefine shared composition membership
- replace the composition session as the source of truth

Plain-English rule:
- focus can point at composition; focus cannot be composition

### Locked Shared Viewer Render Rule

The first-pass shared viewer should render:
- the union of resolved participating graph contributions

Resolved members:
- contribute their viewer-facing preview/renderables to the shared viewer

Unresolved members:
- remain visible as composition members in UI state
- render nothing into the shared viewer until they have a resolved contribution

Render/composition order:
- use explicit composition membership order if the implementation stores it
- if explicit ordering is not stored yet, fall back to graph document order

Do not require in the first pass:
- per-output-entry composition rules
- project-component composition rules
- deeper object/part conflict resolution
- final assembly semantics

Plain-English rule:
- resolved members render; unresolved members stay members but do not render

### Locked Fallback / Default Behavior

If no shared composition session exists yet:
- keep today's single `viewerTargetGraphDocumentId` behavior as the default fallback

Once the user explicitly starts a shared composition:
- the shared composition session becomes the viewer's active composition source
- a one-graph composition is valid as the trivial first composed state

Focus changes may:
- support convenience actions
- suggest likely next members to add

Focus changes must not:
- silently redefine shared composition membership
- collapse the shared viewer back into implicit single-target behavior

Why this cut is correct:
- it preserves current behavior until the user opts into composition
- it gives the phase a clean migration path from current single-target viewer logic
- it avoids a confusing empty viewer or over-implicit auto-composition rule

Plain-English rule:
- default to today's viewer-target behavior until the user explicitly creates shared composition

  - `editorViewportsById`
  - `editorViewportOrder`
  - `activeEditorViewportId`
  - `viewerTargetGraphDocumentId`
- already owns the workspace/runtime coordination seam that should hold first-pass shared composition truth
- does not yet own:
  - multi-member shared composition session state
  - explicit viewport-authored composition membership
  - resolved-union shared-viewer membership selectors

`ViewerHost.tsx`
- currently renders one graph-targeted preview path at a time
- already uses viewer-target selectors that can serve as the fallback/default path
- is the reader that will need to switch between:
  - current single-target fallback behavior
  - active shared composition behavior

`SpaghettiPanel.tsx`
- is already viewport-bound through `editorViewportId`
- is the correct first-pass authoring surface for explicit membership actions because it already represents one editor viewport at a time

`BrowserPanel.tsx`
- should remain out of scope for first-pass composition authoring
- can later gain composition-related actions in later Browser/workspace phases

### Implementation Order

1. Add shared composition session state and explicit membership identity to `useSpaghettiStore`.
2. Add explicit viewport-authored membership actions tied to existing editor viewports.
3. Add selectors that resolve:
   - active shared composition membership
   - participating graph document ids
   - union-of-resolved viewer contributions
4. Keep the current single `viewerTargetGraphDocumentId` path as the fallback/default path.
5. Update the shared viewer read path so it can switch between:
   - fallback single-target behavior
   - active shared composition behavior
6. Add simple visible membership cues on the first-pass viewport authoring surface.
7. Stop before detached windows, Browser-side composition authoring, or later workspace-presentation polish.

### Acceptance / Proof Bar

`SP - Phase 12` counts as real only when tests and workspace behavior prove:

1. The user can explicitly add more than one graph/editor viewport's graph document into one shared composition session.
2. The shared viewer renders the resolved union of participating graph contributions.
3. Unresolved participating graphs remain members but contribute no viewer renderables.
4. Focus changes do not silently change composition membership.
5. If no shared composition session exists, current single `viewerTargetGraphDocumentId` behavior still works.
6. Removing a participating graph updates the visible shared viewer result deterministically.
7. Stale or wrong-graph preview/build state does not leak across composition membership boundaries.
8. Shared composition truth is still clearly separate from graph/project ownership truth.

### Phase Completion Rule

`SP - Phase 12` is complete only when one honest shared viewport composition seam exists, composition truth no longer depends on focused viewport or active-graph convenience state, the shared viewer can present resolved contributions from more than one graph document, and the app still preserves today's single viewer-target behavior when the user has not explicitly started shared composition.
