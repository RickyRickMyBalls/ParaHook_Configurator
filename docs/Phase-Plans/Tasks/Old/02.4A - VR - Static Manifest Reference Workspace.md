## Scope

This phase covers:
- the first Browser `References` subtree inside the `Content` area
- a static checked-in reference manifest as the v1 source of truth
- first-pass loading of `.obj`, `.glb`, and `.stl` files as viewer reference context
- first-pass category parents:
  - `Footpads`
  - `Shoes`
  - `Premade Foothooks`
- lazy loading on first toggle
- per-item and per-category visibility toggles
- calm blue/gray viewer-state bars instead of content build bars
- basic project-versus-reference visibility separation

This phase does not cover:
- folding references into first-pass `Project File` ownership
- runtime folder scanning
- `.step` loading
- remove/unload actions
- viewer selection/editing behavior for references
- rich per-reference material editing
- rich Browser context menus for references
- packaging/export behavior
- deeper published-content build/runtime truth

Working scope rule:
- `02.4A` should add a real reference workspace layer without turning references into published content or pulling in later `[2.5]` richness

## Arch Spec

### Spec Target

This implementation target is only:
- `[2.4A] VR - Static Manifest Reference Workspace`

This cut intentionally sits:
- after the shipped Browser/content structure work from `[2.2]` and `[2.3]`

Plain-English rule:

### Problem Statement

The Browser and viewer now have honest project `Content`, but there is still no first-class reference workspace layer.

Without `02.4`, the app is missing a clear way to:
- surface legacy reference assets in the Browser
- keep references visually near project content without blurring ownership
- show which references are on/off in the viewer
- prepare the later richer reference/material control lane without skipping the simple first layer

`02.4A` needs to add that first reference layer while staying small and honest:
- static manifest, not folder scanning
- viewer-state bars, not build bars
- toggleable context assets, not project-owned content

### Reasonable Phase Cut

`02.4A` should stay small enough to ship as the first usable reference-asset workspace layer.

This phase should actually do:
- place `References` visually inside the `Content` tree above the first assembly row
- replace the special-case `Content` header feel with a connected tree-shell presentation
- load supported reference assets lazily from a static manifest
- toggle child items and whole categories on/off in the viewer
- preserve loaded meshes after first load so re-show is fast
- keep failed rows visible in-tree with muted/error state

This phase should not try to solve:
- project ownership for references
- rich per-row controls
- selection/editing tools
- `.step` support

### Locked Browser Structure Rule

The Browser should move toward this top tree:
- `Project Browser`
  - `Content`
    - `References`
      - `Footpads`
      - `Shoes`
      - `Premade Foothooks`
    - published assembly/content rows
  - `Graph Documents`
  - `Open Editors`

Rules:
- remove the redundant inner `Project` header in this phase
- `Content` should use the same connected tree-shell style as other Browser rows
- `Content`, `References`, and category parents all use normal `+/-` tree controls
- the Browser should draw normal connector lines from `Content` into `References` and from `References` into its categories/items
- `Premade Foothooks` stays visible as a category even if it has no supported loadable children in v1

### Locked Ownership And Source Model

V1 source model is:
- a static checked-in manifest in app code

It is not:
- project-owned content
- runtime folder scanning
- ad hoc UI hardcoding with no manifest layer

Manifest responsibilities:
- display label
- category id
- exact public asset path
- supported file type
- placeholder/support status

Display labels stay:
- `Footpads`
- `Shoes`
- `Premade Foothooks`

Actual current disk roots stay:
- `public/ReferenceModels/footpads/`
- `public/ReferenceModels/shoes/`
- `public/ReferenceModels/hooks/`

Supported v1 file types only:
- `.obj`
- `.glb`
- `.stl`

Out of scope in this phase:
- `.step`

Plain-English ownership rule:
- references live in the workspace/viewer layer and may remember source-path/state, but they are not real published `Content` and not first-pass `Project File` truth

### Locked Category And Item Model

Create these category ids:
- `footpads`
- `shoes`
- `premade-foothooks`

Create these display labels:
- `Footpads`
- `Shoes`
- `Premade Foothooks`

V1 manifest/content reality:
- `Footpads` contains supported `.obj` items from `public/ReferenceModels/footpads/`
- `Shoes` contains supported `.glb` items from `public/ReferenceModels/shoes/`
- `Premade Foothooks` is a placeholder category with no active loadable children in v1 because current hook assets are `.step`

### Locked Interaction Rule

Child reference item rows:
- click row = toggle that single item on/off in the viewer
- `+/-` does not appear on leaf rows

Category rows:
- click row = toggle the whole category on/off in the viewer
- `+/-` = expand/collapse only

`References` root row:
- `+/-` expands/collapses the subtree
- do not use root-row click as a separate visibility toggle in v1

### Locked Visibility And Viewer-State Rule

References default to:
- off/hidden on first app load

Child item row states:
- `blue` = visible/on
- `gray` = hidden/off
- muted/error state = failed load

Category aggregate state:
- `blue` if any child is on
- `gray` if none are on
- category click turns all children off if any are on
- category click turns all supported children on if none are on

Error rule:
- failed rows stay visible in the tree
- they show a muted/error presentation instead of disappearing

### Locked Loading Rule

Rows exist immediately from the static manifest.

Actual mesh loading rule:
- first toggle-on triggers load
- load is lazy per item
- loading state transitions:
  - `unloaded`
  - `loading`
  - `loaded`
  - `error`

Turning a row off:
- hides it
- does not unload it

Turning a loaded row back on:
- reuses the cached loaded mesh
- does not reload from disk

### Locked Passive Context Rule

In `02.4A`, references are passive viewer context only.

That means:
- no build/rebuild bars
- no build/policy semantics
- no remove/unload actions
- no viewer selection/editing semantics
- no rich materials/context-menu surface yet

## Acceptance / Proof Bar

Browser structure acceptance:
- `References` appears above the first assembly inside `Content`
- category parents render in this order:
  - `Footpads`
  - `Shoes`
  - `Premade Foothooks`
- `Premade Foothooks` appears as an empty placeholder category
- `Content` and `References` use normal expandable tree-shell presentation with connector lines

Interaction acceptance:
- clicking a child reference row toggles only that item
- clicking a category row toggles the whole category
- `+/-` expands/collapses without changing visibility
- references start off by default on first load

State/loading acceptance:
- first toggle-on moves an item from `unloaded` to `loading` to `loaded`
- toggle-off hides but does not unload
- second toggle-on reuses the already loaded mesh
- failed loads keep the row visible with error state

Asset acceptance:
- `Footpads` OBJ assets load from the manifest/public path and can be toggled
- `Shoes` GLB assets load from the manifest/public path and can be toggled
- `Premade Foothooks` is visible as a category but has no loadable children in v1

Regression acceptance:
- published `Content` rebuild behavior remains unchanged
- `Graph Documents` and `Open Editors` behavior remains unchanged
