### Problem Statement

After `12A` and `10C`, the app now has:
- a real current `ProjectFile` in `useAppStore`
- explicit project-owned graph membership
- graph-owned published output surfaces per graph
- Browser rows for graphs and open viewports
- parts/debug readers that can consume graph output surfaces directly

But it still does not have:
- project-owned content records above graph output surfaces
- one real root assembly record behind `rootAssemblyId`
- project-owned component records that point back to graph-published output
- a Browser read surface for project content rather than only graph/cached-graph rows

Current runtime still behaves too much like:
- `rootAssemblyId` exists only as a nullable project anchor
- graph-owned output surfaces stop at graph publication truth
- Browser still reads mostly graph/cached-graph state instead of project content structure
- there is no explicit project-owned bundle between graph publication and later Browser-facing output hierarchy

`12B` needs to lift graph-owned publication into project-owned content before cross-graph composition and richer Browser-facing output structure can grow honestly.

### Locked Direction

- extend `useAppStore` with first-pass project content state
- create one real root assembly record and attach it to `currentProject.rootAssemblyId`
- derive first-pass component records from resolved `GraphOutputSurface.entries`
- map one resolved published output entry to one project-owned component
- keep project content app-owned and graph output graph-owned
- add a minimal Browser read surface for `Assembly Root -> Component`
- keep deeper `Object / Part` structure, Browser UX, and cross-graph rules deferred

### Locked First-Pass Project Content Contract

Use this first-pass project-content model:

```ts
type ProjectAssemblyRecord = {
  assemblyId: string
  label: string
  childComponentIds: string[]
}

type ProjectComponentRecord = {
  componentId: string
  sourceGraphDocumentId: string
  sourceOutputEntryId: string
  label: string
}

type ProjectContentState = {
  assembliesById: Record<string, ProjectAssemblyRecord>
  componentsById: Record<string, ProjectComponentRecord>
}
```

Rules:
- one real root assembly record exists behind `currentProject.rootAssemblyId`
- root assembly owns the ordered `childComponentIds`
- component identity is project-owned
- each component carries source references:
  - `sourceGraphDocumentId`
  - `sourceOutputEntryId`
- no first-pass `objectId` records
- no first-pass `partId` records

Important rule:
- this is the first project-owned content model
- it is first-pass project-owned runtime composition state, not durable project-file persistence yet
- it is not the final Browser-facing hierarchy and not the final output structure

### Locked Component Mapping Rule

First-pass component mapping is:
- one project-owned component per resolved published output entry from `GraphOutputSurface.entries`

Rules:
- component creation is driven by graph-owned output publication, not viewport state
- one graph may produce multiple first-pass components if it publishes multiple resolved output entries
- do not hard-lock first-pass content ownership to exactly one component per graph
- component labels may derive from output entry labels in first pass

Plain-English rule:
- graph-published output becomes project-owned component content

### Locked Ownership Boundary

`useAppStore` owns:
- current `ProjectFile`
- `ProjectContentState`
- root assembly and component records
- project-content selectors/read models
- minimal Browser read models for project content

`useSpaghettiStore` continues to own:
- graph documents
- graph-local runtime
- graph-owned output surfaces
- cached graph entries
- editor viewport state
- viewer-target state

`GraphOutputSurface` remains:
- graph-owned publication truth

Project content becomes:
- the project-owned composition layer built from graph-owned publication truth

Plain rule:
- graph says what is published
- project says where published components live

### Locked Graph-Versus-Project Authority Rule

Graph owns:
- what it publishes
- the authored output declaration
- the internal meaning of the published bundle

Project owns:
- the root assembly record
- which assembly contains which component
- higher-level placement and containment above graph-published output

So:
- graph-owned truth says:
  - `I publish this output`
- project-owned truth says:
  - `This output now exists here as project component content`

Working rule:
- Browser/project composition must not silently rewrite graph publication meaning

### Implementation Order

1. Add first-pass `ProjectContentState` to the app-owned project layer.
2. Create one real root assembly record and connect it to `currentProject.rootAssemblyId`.
3. Read graph-owned output surfaces from spaghetti store.
4. Derive first-pass project component records from current resolved graph output entries.
5. Map one resolved published output entry to one project-owned component.
6. Store source references on each component:
   - `sourceGraphDocumentId`
   - `sourceOutputEntryId`
7. Expose selectors for:
   - root assembly
   - ordered child components under root
   - component by id
8. Add a minimal Browser read surface showing:
   - `Project`
   - `Assembly Root`
   - `Component` rows
9. Keep row actions, deep hierarchy, and Browser/workspace polish out of scope.

Working rule:
- first pass may derive project content from graph output surfaces rather than persisting a richer authored project-content editing system

### Acceptance / Proof Bar

`12B` counts as real only when tests prove:

1. One real root assembly record exists when a current project exists.
2. Root assembly identity is connected through `currentProject.rootAssemblyId`.
3. Component records are created from graph output entries, not inferred from viewport state.
4. One resolved output entry creates one component record.
5. Multiple resolved output entries from one graph can create multiple component records.
6. Component records preserve source references to graph document and output entry.
7. Browser focus/editor focus changes do not redefine project content structure.
8. Viewer-target changes do not redefine project content structure.
9. No required dependency on `objectId` or `partId` exists in first pass.
10. Minimal Browser read surface can read root assembly and component rows from project-owned state.

Minimum acceptance statement:
- `12B` is complete only when project content ownership is real above `12A`, first-pass component records are derived from graph-published outputs, and the Browser can read a minimal `Assembly Root -> Component` structure without collapsing back into flat graph-only ownership.
