### Problem Statement

The repo already has partial publication structure:
- authored `OutputPreview` params
- graph-owned published-output derivation
- project-owned content records
- Browser content rows

But the current docs and code-adjacent language still blur:
- `Graph Documents` versus published `Content`
- singleton published objects versus grouped component hierarchy
- graph-owned publish declarations versus project-owned lifted content

`02.2` needs to lock one truthful first-pass publication model so later Browser/build-control work can attach to stable structure instead of guessing from slots, meshes, or placeholder grouping rows.

### Locked First-Pass Publish Contract

Phase 5 uses an authored publish contract of:
- `objects[]`
- `slots[]`
- `nextSlotIndex`

Contract rules:
- `objects[]` is the canonical first-pass authored publish seam
- `componentLabel` is conditional metadata:
  - ignore it for singleton publish groups
  - only make it meaningful when a publish group has two or more objects and needs a real visible component row
- empty authored `objects[]` entries may remain in authored state as setup scaffolding
- authored empty objects must not lift into Browser `Content`
- slot/runtime compatibility stays intact in this phase:
  - slots remain the preview/runtime compatibility layer
  - Browser `Content` must stop reconstructing structure from slots directly

### Locked Singleton Versus Grouped Hierarchy Rule

The first shipped Browser `Content` hierarchy is conditional:
- singleton published object:
  - `Assembly -> Object`
- multi-object publish group:
  - `Assembly -> Component -> Object`

Hierarchy rules:
- `Assembly` is the single root assembly for the project-content surface in this phase
- `Component` exists only when hierarchy is actually needed for two or more objects from one publish group
- a singleton published object must not get a redundant visible parent `Component`
- `Object` is the first real published row, whether it sits directly under the root assembly or under a grouped component
- if a singleton later becomes multi-object:
  - the original object keeps its `objectId`
  - the new grouping layer receives the new `componentId`
  - only new sibling objects receive new `objectId` values
- `Part` is explicitly deferred out of this phase

### Locked Stable Id And Ownership Split

Stable Phase 5 id model:
- `assemblyId`
- conditional `componentId`
- `objectId`
- future `partId`

Ownership split:
- graph-owned authored publish declarations live in `OutputPreview` params
- graph-owned derived publish surfaces are produced after graph evaluation
- project-owned content records own lifted published entities used by Browser `Content`
- later runtime/execution truth belongs to the later build/runtime lane, not Phase 5 selectors

Identity rules:
- `componentId` exists only for multi-object publish groups that become real grouping entities
- root/sub assembly differences are hierarchy relationships, not different id families
- later policy, revision, and execution truth must be able to attach without replacing `assemblyId`, `componentId`, or `objectId`

### Locked Graph-To-Project Lift

The lift path for this phase is:
- authored `OutputPreview` publish declarations
- graph-owned runtime/output surface
- graph-owned derived publish surface
- project-owned content records
- Browser read-model rows

Lift rules:
- the graph layer owns publish derivation and filtering of publishable entities
- the project layer owns stable content ids and records for `Assembly`, conditional `Component`, and `Object`
- singleton publish groups collapse during the lift:
  - one published object lifts directly under the root assembly
  - two or more published objects from one publish group lift under a component row
- if one graph document has multiple separate singleton publish groups, each one lifts as its own direct object row under the root assembly with no extra synthetic graph-document grouping row
- Browser selectors derive read shape, nesting, and ordering from project-owned content records rather than inventing ownership locally

### Locked Source-Trace Carry-Forward

Phase 5 must preserve at least:
- `sourceGraphDocumentId`
- `sourceNodeId`
- `sourceOutputEntryId`
- `slotId`

Source-trace rules:
- Browser content rows must carry enough source data for:
  - viewer highlight
  - reveal
  - later `view in graph`
  - later right-click authoring jumps
- slot-based highlight/reveal is accepted for Phase 5 where that matches the current preview pipeline
- the spec must state slot-based highlight identity as a limitation rather than implying object-native viewer identity already exists
- receive-link content follows the same visible singleton-collapse rule on the Browser surface, even if its internal implementation remains lighter until later work
