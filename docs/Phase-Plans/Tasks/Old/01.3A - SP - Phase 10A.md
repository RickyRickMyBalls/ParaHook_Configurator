### Problem Statement

After `9C`, the app now has:
- graph-local compile/build bridge memory in `useSpaghettiStore`
- graph-keyed pending build state
- Browser/editor graph identity that is no longer purely singleton

But it still does not have:
- one explicit graph-routed request envelope for compile and build
- one explicit graph-routed result envelope for compile and build
- graph-local ownership of routing truth for `buildSeq` and in-flight request identity
- graph-aware stale-drop enforcement
- canonical graph-routed entry points for compile/build

Current runtime still behaves too much like:
- `compileSpaghetti()` and `requestSpaghettiBuild()` infer one active graph
- `BuildDispatcher` keeps one app-global stale-drop path through `latestRequestedSeq` and `latestResolvedSeq`
- `bootstrapBuildWiring.ts` reads spaghetti pending-state through one active graph path
- `protocol.ts` worker request/result messages do not carry graph/project routing identity

`10A` needs to make request/result routing graph-aware before `10B` takes on the broader runtime-memory cut.

### Locked Direction

- use one shared outer request envelope for compile and build
- use one shared outer result envelope for compile and build
- keep `buildSeq` truth graph-local
- keep primary stale-drop enforcement in routing/result handling
- add a defensive stale/wrong-target write guard in graph-runtime setters
- keep focus changes from rebinding in-flight result ownership
- keep compile local in first-pass `10A`
- keep build routed through the shared worker path in first-pass `10A`
- keep old singleton-shaped compile/build helpers only as thin temporary wrappers
- use one synthetic runtime `projectFileId` until `GE - Phase 12` introduces real project ownership

### Locked Request Contract

Use one shared graph-routed outer request envelope for both compile-only and build requests.

```ts
type GraphBuildRequestKind = 'compile' | 'build'

type GraphBuildRequestEnvelope = {
  requestKind: GraphBuildRequestKind
  projectFileId: string
  graphDocumentId: string
  buildRequestId: string
  buildSeq: number
  payload: CompileRequestPayload | BuildRequestPayload
}
```

Rules:
- both compile and build use the same outer routing shape
- both always carry:
  - `projectFileId`
  - `graphDocumentId`
  - `buildRequestId`
  - `buildSeq`
- only `requestKind` and `payload` differ
- `buildRequestId` may be an opaque routing-layer id with no user-visible format rule

First-pass implementation defaults:
- `projectFileId` is synthetic runtime identity only
- it should live as one temporary routing-level value in spaghetti runtime state, not as a persisted project-file id
- compile uses the canonical request envelope shape but is handled locally
- build uses the canonical request envelope shape and continues through dispatcher/worker routing

### Locked Result Contract

Use one shared outer result envelope that echoes the routing identity from the request.

```ts
type GraphBuildResultKind = 'compile' | 'build'
type GraphBuildResultStatus = 'ok' | 'error' | 'partial'

type GraphBuildResultEnvelope = {
  resultKind: GraphBuildResultKind
  status: GraphBuildResultStatus
  projectFileId: string
  graphDocumentId: string
  buildRequestId: string
  buildSeq: number
  diagnostics?: GraphDiagnostic[]
  payload?: CompileResultPayload | BuildResultPayload
}
```

Acceptance rule:
- a result may be accepted only if:
  - `projectFileId` matches the current runtime project id
  - `graphDocumentId` matches the target graph runtime bucket
  - `buildSeq` is still valid for that graph
  - `buildRequestId` matches the graph's in-flight/latest request identity when checked

Important rule:
- full, partial, and diagnostics-only results all use the same acceptance rules
- wrong-graph results are rejected
- stale same-graph results are rejected

### Locked Graph Routing Runtime Contract

`buildSeq` truth should live per graph in graph-local runtime state.

```ts
type GraphRoutingRuntimeState = {
  latestIssuedBuildSeq: number
  latestAcceptedBuildSeq: number | null
  inFlightBuildRequestId: string | null
  inFlightBuildSeq: number | null
}
```

Rules:
- `latestIssuedBuildSeq` is the primary stale-drop truth
- `latestAcceptedBuildSeq` exists for accepted-result/runtime inspection truth
- dispatcher code may mirror routing state temporarily, but it is not the canonical owner
- the existing `graphDocumentIdByBuildSeq` mapping is only a bridge seam and should not remain the final `10A` routing contract

### Locked Entry-Point Rule

Canonical first-pass APIs:

```ts
compileGraphDocument(graphDocumentId: string): CompileResult
requestGraphDocumentBuild(graphDocumentId: string): CompileResult
```

Rules:
- these are the real first-pass compile/build entry points
- they must require explicit `graphDocumentId`
- they keep synchronous compile-result returns in first-pass `10A` for UI compatibility

Compatibility bridge:
- `compileSpaghetti()` and `requestSpaghettiBuild()` may remain briefly
- they must become thin wrappers only
- they must stop inferring one "current spaghetti graph" from singleton state
- they must forward directly into the canonical graph-routed APIs

### Locked Focus / Ownership Rule

In-flight builds stay bound to the graph they were issued for.

Rules:
- request ownership follows `graphDocumentId`
- not focused viewport
- not focused Browser row
- not current viewer target

Practical result:
- if Graph A starts a build and focus later switches to Graph B, the returning result still belongs only to Graph A
- a non-focused graph may still show in-flight or completed build status later

### Current Seams This Phase Must Cut

1. `useAppStore` still owns singleton-shaped spaghetti compile/build entry points
2. `BuildDispatcher` still uses one app-global `seq` stale-drop path
3. `bootstrapBuildWiring.ts` still reads spaghetti pending build data from one active-graph path
4. `useSpaghettiStore` does not yet expose the full graph-local routing runtime contract
5. `protocol.ts` does not yet carry graph/project routing identity through worker messages

### Current Seam Findings

#### `useAppStore.ts`

Current seam:
- `compileSpaghetti()` reads the active graph from `useSpaghettiStore`
- `requestSpaghettiBuild()` reads the active graph, compiles it, stages runtime state, and enters the dispatcher through one active-graph shell helper

`10A` consequence:
- these must stop being the canonical compile/build APIs
- they become migration wrappers around explicit graph-routed entry points
- compile remains locally handled, but identity must stop being inferred

#### `buildDispatcher.ts`

Current seam:
- `seqCounter`, `latestRequestedSeq`, and `latestResolvedSeq` are app-global
- stale-drop is enforced as one shared dispatcher rule rather than one graph-aware rule
- worker requests/results currently carry only the existing build/assemble identities

`10A` consequence:
- spaghetti routing must stop relying on one app-global stale-drop path
- dispatcher stale-drop for spaghetti mode must become graph-aware
- shared dispatcher infrastructure may stay shared, but graph identity must travel through build request/result handling

#### `bootstrapBuildWiring.ts`

Current seam:
- spaghetti providers still pull changed-param ids, instances, and part keys from the active graph pending-state path
- build results still flow back through one shared handler path

`10A` consequence:
- routing/result handling must become graph-aware
- the wiring layer becomes the primary acceptance/rejection seam for spaghetti results
- focus changes must not rebind accepted result ownership

#### `useSpaghettiStore.ts`

Current seam:
- graph runtime already stores bridge compile/build memory
- `stageGraphBuildRequest(...)`, `acceptGraphBuildResult(...)`, and `clearGraphBuildRequest(...)` still use the earlier bridge contract
- explicit routing fields for latest issued seq, latest accepted seq, and in-flight request identity are not yet the formal contract

`10A` consequence:
- add the graph-local routing runtime fields
- add a defensive stale/wrong-target setter guard
- keep graph runtime truth graph-local instead of app-global

#### `protocol.ts`

Current seam:
- worker message schemas still lack:
  - `projectFileId`
  - `graphDocumentId`
  - `buildSeq` as graph-routed acceptance identity
  - `buildRequestId` as graph-routed acceptance identity

`10A` consequence:
- build-side worker request/result messages must grow the graph-routed identity fields
- compile does not need a worker round-trip in first-pass `10A`, but it still uses the same canonical outer routing contract locally

### Implementation Sequence

1. Add the canonical graph-routed compile/build APIs:
   - `compileGraphDocument(graphDocumentId)`
   - `requestGraphDocumentBuild(graphDocumentId)`
2. Add the synthetic runtime `projectFileId` and the graph-local routing runtime fields to spaghetti runtime state.
3. Convert compile request creation to the canonical graph-routed request contract, but keep compile handled locally.
4. Convert build request creation and worker protocol messages to carry the graph-routed identity fields.
5. Convert result handling to the canonical result contract and perform graph-aware acceptance checks in routing/result handling.
6. Add the defensive graph-runtime stale/wrong-target write guard.
7. Keep old compile/build helpers only as thin migration wrappers and update call sites to pass explicit `graphDocumentId`.

### Acceptance Criteria

`10A` counts as done only when:
- compile/build requests no longer depend on inferring one singleton spaghetti graph
- accepted/rejected results are decided by graph-aware routing identity
- in-flight result ownership does not change when editor/Browser/viewer focus changes
- graph-local routing truth owns `buildSeq` and in-flight request identity
- the seven required proof-bar tests exist and pass

This phase is not allowed to claim:
- full graph-local preview/build payload ownership
- final shared-viewer targeting behavior
- output handoff structure
- real persisted `projectFileId` ownership
