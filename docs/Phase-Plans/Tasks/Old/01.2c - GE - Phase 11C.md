## Arch Spec

### Spec Target

This implementation target is only:
- `[1.2C] GE - Phase 11C - Save/Load Interaction With Editors`

This cut is intentionally narrow:
- keep Browser row click as `open-or-focus`
- add explicit same-graph multi-viewport open behavior
- add explicit focused-viewport swap behavior
- split `Load Into New Graph` from raw file-open behavior by cloning into a new graph identity
- route editor save through the focused viewport's bound graph and existing cached-entry save seam

If this cut is wrong, later work has no stable base for:
- predictable Browser/editor coordination
- multi-viewport editing on top of shared graph truth
- explicit clone-versus-reopen behavior
- `GE 12` project-level graph collection ownership above the current Browser/store layer

### Problem Statement

After shipped `11A` and `11B`, the app now has:
- durable graph-document save/load
- Browser-owned cached graph entries
- one Browser graph row click behavior:
  - `open-or-focus`
- editor viewports that can already rebind to a different graph document

But it still does not have:
- explicit Browser secondary actions for `Open In New Editor` or `Swap Current Editor`
- an explicit editor-side save target
- a first-pass `Load Into New Graph` path that intentionally clones file contents into a new graph identity
- a written rule for how Browser selection/focus follows viewport rebinding actions

Current runtime still behaves too much like:
- `openGraphDocumentInViewport(...)` is both the only Browser open path and the only viewport-open path
- `loadGraphDocumentFromFile(...)` preserves the loaded file's `graphDocumentId`
- the Browser has no explicit `11C` row actions beyond row click plus save
- the editor can switch graphs via dropdown, but that does not yet define the broader save/load action model

`11C` needs to make the editor-facing actions explicit before later Browser/project ownership phases deepen the model.

### Locked Direction

- `11C` owns the explicit editor interaction layer on top of the shipped `11A` and `11B` seams
- Browser cached entries remain Browser-owned lifecycle objects
- editor viewports remain UI binding/window objects only
- `Open Graph`, `Load Into New Graph`, `Open In New Editor`, and `Swap Current Editor` must stay distinct
- `Import Into Current Graph` remains a named separate action, but stays out of first-pass `11C` implementation scope
- editor save should reuse the cached-entry save seam instead of introducing a second direct file-IO path
- Browser selection/focus should follow explicit viewport-rebinding actions in first pass

### Locked Ownership Roles

- `GraphDocument`
  - authored graph truth
  - durable graph-level identity
- `CachedGraphEntry`
  - Browser-owned lifecycle wrapper around one live graph document
  - save/load lifecycle surface
- `EditorViewport`
  - UI binding/window object
  - points at one `graphDocumentId` at a time
  - is not graph truth and is not cached-entry truth

Practical rule:
- graph identity, cached-entry identity, and viewport identity must remain separate concepts even when first-pass ids still coincide in some store paths

### First-Pass Editor Action Model

Use this first-pass action model:

```ts
type EditorLoadAction =
  | 'openGraph'
  | 'loadIntoNewGraph'
  | 'openInNewEditor'
  | 'swapCurrentEditor'
```

Named but out-of-scope companion action:

```ts
type DeferredGraphMergeAction = 'importIntoCurrentGraph'
```

Rules:
- `Open Graph`
  - reuses the existing Browser row-click `open-or-focus` path
- `Load Into New Graph`
  - loads file contents into a fresh live graph identity
  - creates a fresh cached Browser entry
  - does not preserve the loaded file's live `graphDocumentId`
- `Open In New Editor`
  - opens another viewport on the same graph document
  - does not clone the graph
- `Swap Current Editor`
  - rebinds the focused viewport to another graph document
  - does not open a new viewport
- `Import Into Current Graph`
  - remains a separate merge action
  - is named here only to prevent the implementation from collapsing it into `Load Into New Graph`

### Locked Action Matrix

#### `Open Graph`

- trigger surface:
  - Browser graph row click
- target object:
  - existing Browser cached graph entry / graph document
- viewport effect:
  - call the existing `openGraphDocumentInViewport(graphDocumentId)` path
  - focus the existing viewport if one already exists for that graph
  - otherwise open a new viewport
- identity effect:
  - none
- Browser focus effect:
  - Browser stays/focuses on the targeted graph row

#### `Load Into New Graph`

- trigger surface:
  - explicit Browser/file-load action after the user chooses a graph file from disk
- target object:
  - loaded graph-document payload from file
- viewport effect:
  - none immediately in first pass
  - the action creates a new Browser-targetable graph row first
  - that new graph can then be used with `Open Graph`, `Open In New Editor`, or `Swap Current Editor`
- identity effect:
  - always clone into a fresh live `graphDocumentId`
  - always create a fresh cached-entry identity
  - the new copy starts dirty because it is now an unsaved working copy distinct from the source file
- Browser focus effect:
  - Browser focus/selection moves to the new graph row once created

#### `Open In New Editor`

- trigger surface:
  - explicit Browser row secondary action
- target object:
  - existing Browser cached graph entry / graph document
- viewport effect:
  - open a new focused viewport bound to that graph document
  - allow multiple viewports to point at the same graph document in first pass
- identity effect:
  - none
- Browser focus effect:
  - Browser focus/selection follows the graph bound to the new focused viewport

#### `Swap Current Editor`

- trigger surface:
  - explicit Browser row secondary action
- target object:
  - existing Browser cached graph entry / graph document
- viewport effect:
  - rebind the currently focused viewport to that graph document
  - if no focused viewport exists, the action is disabled
  - if somehow invoked anyway, it no-ops rather than opening a new viewport
- identity effect:
  - none
- Browser focus effect:
  - Browser focus/selection follows the graph bound to the affected focused viewport

### Locked Save Target Rules

- Browser-side save:
  - targets the selected Browser cached graph row
  - uses the existing `saveCachedGraphEntryToFile(...)` seam
- editor-side save:
  - targets the graph bound to the focused editor viewport
  - resolves:
    - focused viewport
    - `graphDocumentId`
    - matching cached graph entry
    - `saveCachedGraphEntryToFile(...)`
- first pass should not invent a second direct graph-document file-save path for editor save
- if there is no focused viewport, editor-side save is disabled

### Current Seam Vs Required Change

#### `src/app/spaghetti/store/useSpaghettiStore.ts`

Current seam:
- `openGraphDocumentInViewport(graphDocumentId)` is the current `open-or-focus` path
- `bindEditorViewportToGraphDocument(editorViewportId, graphDocumentId)` already rebinds a viewport
- `loadGraphDocumentFromFile(...)` currently preserves the file's `graphDocumentId`
- `saveCachedGraphEntryToFile(...)` already exists as the file-save seam
- current open behavior enforces one viewport per graph document

Required `11C` change:
- keep `openGraphDocumentInViewport(...)` unchanged as the `Open Graph` path
- add an explicit same-graph multi-viewport open path
- add an explicit focused-viewport swap path
- add a distinct file-load-into-new-graph path that clones file contents into a fresh graph identity
- add an editor-save helper that resolves the focused viewport to the correct cached-entry save target
- keep Browser focus/selection synced through the existing active graph / active viewport bridge instead of adding a new Browser-only selection model in first pass

Recommended first-pass store surface:

```ts
openGraphDocumentInViewport(graphDocumentId: string): string | null
openGraphDocumentInNewViewport(graphDocumentId: string): string | null
swapFocusedEditorViewportToGraphDocument(graphDocumentId: string): string | null
loadGraphDocumentIntoNewGraphFromFile(options?): Promise<string>
saveFocusedEditorViewportGraphToFile(options?): Promise<void>
```

Behavior rules:
- `openGraphDocumentInNewViewport(...)`
  - always creates a new viewport
  - does not de-dupe against existing same-graph viewports
- `swapFocusedEditorViewportToGraphDocument(...)`
  - reuses current viewport-binding semantics
  - returns `null` and no-ops if no focused viewport exists
- `loadGraphDocumentIntoNewGraphFromFile(...)`
  - loads a file through the existing `11A` IO seam
  - clones the loaded graph contents
  - creates a fresh graph document and cached entry
  - marks the new entry dirty
  - selects/focuses the new Browser row
- `saveFocusedEditorViewportGraphToFile(...)`
  - resolves the focused viewport's graph through cached-entry state
  - delegates to `saveCachedGraphEntryToFile(...)`

#### `src/app/panels/BrowserPanel.tsx`

Current seam:
- Browser graph rows already use cached entries
- row click is already `open-or-focus`

Required `11C` change:

- route top-level file-load into the new `Load Into New Graph` path instead of the current identity-preserving file-load path

#### `src/app/spaghetti/ui/SpaghettiEditor.tsx`

Required `11C` change:

- if a first-pass editor-side save control is added here or in `SpaghettiPanel`, keep its semantics identical to the locked focused-viewport save rule

# Close Out notes

What landed cleanly:
- `useSpaghettiStore` was the correct first-pass home for the explicit `11C` editor actions
- Browser row click could remain `open-or-focus` while secondary row actions owned `Open In New Editor` and `Swap Current Editor`
- focused-editor save could reuse the cached-entry save seam instead of introducing a second save path

What mattered most:
- the most important identity split was:
  - durable graph file
  - live graph document
  - Browser cached entry
  - editor viewport
- `Load Into New Graph` needed to break identity on purpose instead of preserving the file's live `graphDocumentId`

Behavior notes:
- Browser row click remains `Open Graph`
- `New Editor` allows more than one viewport on the same graph document
- `Swap Editor` rebinding requires a focused viewport and otherwise no-ops
- `Load Into New Graph` creates a fresh dirty working copy
- editor-side save now follows the focused viewport's graph binding

Carry-forward notes:
- `Import Into Current Graph` is still deferred and remains a separate explicit action
- `GE 12` should own any later project-level graph collection ownership above the current Browser/store layer
- later Browser workspace phases should own richer row polish and context-menu behavior beyond the first-pass `11C` buttons
