### Problem Statement

After `12A`, `12B`, and `10C`, the app now has:
- a real current `ProjectFile`
- explicit project-owned graph membership
- explicit project-owned `Assembly Root -> Component` content structure
- graph-owned published output surfaces with stable output-entry identity
- Browser and parts/debug readers that can already consume graph-owned or project-owned surfaces honestly

But it still does not have:
- a first-pass cross-graph authored reuse model
- a defined place where one graph can declare that it receives output from another graph
- a first-pass `Link` versus `Hard Copy` rule
- an explicit cross-graph reference contract tied to stable ids
- protection against current active-graph, viewer-target, and focused-viewport convenience state being mistaken for ownership truth

Current runtime still behaves too much like:
- each graph is mostly an isolated authored/runtime island
- project composition can consume graph-owned publication, but graphs cannot yet explicitly reuse each other through a defined ownership seam
- active graph and viewer-target state remain stronger than they should be as app-wide convenience paths
- Browser/project surfaces have no cross-graph ownership rules to rely on yet

`12C` needs to define the first honest cross-graph ownership seam before later Browser growth and fuller publish/receive execution work can happen without drifting into ad hoc reference behavior.

### Locked Direction

- use an explicit first-pass `Publish / Receive` model across graph documents
- keep the publishing graph as the owner of published output declaration truth
- keep the receiving graph as the owner of authored receive intent only
- default the first pass to `Link`
- define `Hard Copy` conceptually, but defer it as an explicit later ownership-conversion action
- keep cross-graph resolution explicit and id-based
- keep project-owned composition downstream of graph-authored receive intent rather than turning project state into the authored source of truth
- land one honest first-pass linked receive path in code rather than stopping at paper-only ownership rules
- keep Browser-facing structure, hard-copy UX, export semantics, and fuller publish/receive workflow work deferred

### Locked First-Pass Cross-Graph Contract

Use a small explicit first-pass receive-reference contract:

```ts
type GraphReceiveReference = {
  receiveId: string
  sourceGraphDocumentId: string
  sourceOutputEntryId: string
  mode: 'link'
}
```

If needed, the receiving graph may also carry receiver-side authored identity such as:
- `receiveNodeId`

Required first-pass identity:
- `sourceGraphDocumentId`
- `sourceOutputEntryId`
- receiving-graph authored reference identity

Optional project context:
- current `projectFileId` or equivalent project context if routing/validation needs to assert same-project ownership

Do not require in first pass:
- `assemblyId`
- `componentId`
- `objectId`
- `partId`
- Browser row state
- hard-copy metadata
- export/package metadata

Working rule:
- every receive relationship must explicitly say:
  - which graph published
  - which published output entry is linked
  - which authored receiver is consuming it

### Locked `Link` Versus `Hard Copy` Rule

`Link` is the default first-pass cross-graph mode.

`Link` means:
- the receiving graph references source-graph published output by explicit identity
- updates to source publication flow through to the receiver
- the receiver does not become the owner of the source content

`Hard Copy` means:
- create a new owned record or graph-local authored content based on source content at copy time
- after copy, the copied content no longer updates from the original source graph
- copied content becomes owned by the receiving side according to later structure rules

Rules:
- first-pass `12C` defines the ownership distinction clearly
- first-pass `12C` does not require hard-copy UX or conversion flow
- a reference must never silently become a copy

Plain-English rule:
- linked = live reference to source-owned published output
- hard copy = explicit ownership conversion later

### Locked Ownership Boundary

Source graph owns:
- what it publishes
- published output declaration truth
- the internal authored meaning of the published bundle
- the stable `sourceOutputEntryId` identity exposed through graph-owned output surfaces

Receiving graph owns:
- the receive node or equivalent authored reference declaration
- the choice to link to a specific source graph/output entry
- receiver-local unresolved state when the source publication is absent or invalid

Project-owned state may later:
- derive project composition consequences from source publication plus receiving-graph authored receive intent
- organize received results inside project/browser structure

Project-owned state does not:
- author the graph-to-graph relationship
- replace the receiving graph as the source of receive intent

Viewer/workspace state never owns:
- cross-graph relationship truth
- source/receiver identity
- composition authority

Plain rule:
- graph publishes
- graph receives
- project composes
- viewer presents

### Locked Singleton-Breaking Rule

`12C` must explicitly reject these as architecture truth:
- one `active graph` acting as the only meaningful graph
- one viewer-target path standing in for project composition truth
- one focused editor viewport standing in for cross-graph ownership truth
- one global output-consumption path derived from current UI focus
- Browser/editor convenience state acting as ownership state

`12C` must require that:
- cross-graph references resolve by explicit graph/output identity
- project composition does not depend on whichever graph is open or focused
- receiver behavior is not derived from viewer-target or active-editor state
- selectors and read models can resolve source-versus-receiver relationships without relying on singleton UI state

Working rule:
- active graph, focused viewport, and viewer target are workspace conveniences
- they are not ownership or cross-graph composition authority

### Implementation Order

1. Add the first graph-authored receive/reference seam to graph-owned authored state.
2. Keep source publication truth in the existing graph-owned output surface.
3. Resolve linked source publication by explicit:
   - `sourceGraphDocumentId`
   - `sourceOutputEntryId`
   - receiver-side authored identity
4. Represent unresolved state when the source publication is absent, removed, or otherwise invalid.
5. Keep project/browser consumers downstream of that authored relationship.
6. Stop before Browser-facing content structure, hard-copy flow, or broader publish/receive workflow polish.

Working rule:
- `12C` should land one honest linked receive path
- later `Publish / Receive Execution` phases can deepen the full system

### Acceptance / Proof Bar

`12C` counts as real only when tests prove:

1. Receive references resolve by explicit source graph/output identity.
2. Linked receive relationships update when source published output changes.
3. Missing or removed source publication produces a clear unresolved state.
4. Active graph changes do not redefine cross-graph ownership.
5. Focused editor viewport changes do not redefine cross-graph ownership.
6. Viewer-target changes do not redefine cross-graph ownership.
7. Wrong-graph or stale writes cannot overwrite another graph's receive relationship.
8. No label-based or UI-state-based identity inference is required.
9. First pass does not require `assemblyId`, `componentId`, `objectId`, or `partId`.

Minimum acceptance statement:
- `12C` is complete only when one honest linked cross-graph receive seam exists, source publication ownership stays with the publishing graph, receiving-graph authored intent is explicit, and cross-graph resolution no longer depends on active/focused/viewer-target singleton UI state.
