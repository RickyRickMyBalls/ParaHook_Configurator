## Arch Spec

### Spec Target

This implementation target is only:
- `[1.2A] GE - Phase 11A - Graph Document Persistence Core`

This cut is intentionally narrow:
- save one graph document
- load one graph document
- validate and normalize that document
- provide one low-level browser file IO seam
- keep non-durable runtime/editor/browser state out of the saved contract

If this cut is wrong, later work has no stable base for:
- cached graph lifecycle in `11B`
- save/load editor behavior in `11C`
- project-level graph collections in `GE 12`

### Problem Statement

After `SP - Phase 9`, the app has:
- graph documents in live runtime memory
- graph-local authored state
- Browser/open-focus coordination
- graph-local compile/build/preview-prep runtime

But it still does not have:
- a real saved graph-document file contract
- explicit save/load core entry points
- a durable parse/validate path for graph documents
- a dedicated browser file IO surface for graph documents

Current runtime still behaves too much like:
- graph documents exist only in memory
- graph-document schema is runtime-only
- there is no meaningful `src/app/io/` persistence module yet
- Browser and editor work can evolve without a durable file contract holding them still

`11A` needs to make the graph-document contract durable before cached graph lifecycle and editor save/load behavior become deeper.

### Locked Direction

- save/load one graph document at a time in `11A`
- use the existing `GraphDocument` as the durability center
- keep persisted truth limited to graph-document truth
- include pure helpers plus one browser file IO service
- do not persist viewport/browser-local runtime state in this phase

### First-Pass Persistence Contract

Use this first-pass durable contract:

```ts
type GraphDocument = {
  graphDocumentId: string
  name: string
  version: 1
  graph: SpaghettiGraph
}
```

Rules:
- `graphDocumentId` is durable identity
- `name` is durable user-facing document naming
- `version` is required and versioned from the start
- `graph` persists exactly through the existing parse/normalize path
- compile/build runtime buckets are not part of the saved file
- viewport/browser focus/open/window state is not part of the saved file

### Locked Schema / Validation Seam

- `parseGraphDocument()` in `src/app/spaghetti/schema/spaghettiSchema.ts` is the canonical load boundary
- `11A` may add small serialization helpers, but should not create a second graph-document schema
- malformed JSON fails before schema parsing
- malformed graph-document payloads fail at the parse/validation boundary
- legacy graph normalization should continue to come from the existing parse path, not from file IO code

### Locked Save / Load Ownership Rules

- `GraphDocument` is the saved unit in `11A`
- Browser cache policy belongs later in `11B`
- editor-open/swap/import policy belongs later in `11C`
- project-file ownership belongs later in `GE 12`

Practical implication:
- `11A` should expose persistence helpers that can save/load a graph document without deciding how Browser or editor surfaces will consume them

### Locked First IO Surface

Use this first-pass split:

```ts
serializeGraphDocument(document): string
deserializeGraphDocument(json: string): GraphDocument
saveGraphDocumentToFile(document): Promise<void>
loadGraphDocumentFromFile(): Promise<GraphDocument>
```

Rules:
- file format is JSON text
- default extension should be `.parahook-graph.json`
- helper functions stay pure
- browser file IO stays UI-free
- no direct Browser/editor/store policy lives in this phase

# Close Out notes

Use this section after implementation to record:
- what was hardest about separating durable graph truth from runtime/editor state
- whether the first save/load contract feels stable enough for cached-graph lifecycle work
- what must stay in `11B` and `11C` instead of leaking back into `11A`
- whether the pure-helper plus browser-file-IO split stayed clean enough for later UI wiring

Implementation close-out:
- `11A` landed cleanly as a persistence-core cut without pulling Browser/editor interaction policy forward.
- The saved unit is now explicitly `GraphDocument`, not live `useSpaghettiStore` state, which prevented `graphRuntimeByDocumentId`, viewport state, and canvas interaction state from leaking into the file contract.
- Reusing `parseGraphDocument()` as the load boundary was the right choice; it kept schema truth in one place and made `11A` mostly a persistence-surface phase instead of a second-schema phase.
- The browser file IO service stayed low-level and UI-free by using a small `Blob` + anchor download path and a hidden file-input load path. That gives later UI work in `11B` / `11C` a stable service seam without forcing editor policy into this phase.
- The main thing to protect in future phases is identity policy:
  - `11A` preserves `graphDocumentId` on load
  - `11C` should decide when loading should keep identity versus clone/import into a new identity
- `11B` should own Browser cached-graph lifecycle and reopen/focus behavior.
- `11C` should own `Open Graph`, `Load Into New Graph`, `Swap Current Editor`, and `Open In New Editor`.
