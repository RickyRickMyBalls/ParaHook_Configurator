## Arch Spec

### Spec Target

This implementation target is only:
- `[1.4A] GE - Phase 12A - Project File Core And Graph Collection Ownership`

This cut intentionally sits:
- after `GE - Phase 11`, which already made graph-document persistence and cached graph lifecycle real

### Problem Statement

After `GE - Phase 11` and `SP - Phase 10C`, the app now has:
- durable single-graph save/load
- Browser-owned cached graph entries
- multiple graph documents in spaghetti store state
- graph-local runtime ownership
- graph-aware request/result routing fields

But it still does not have:
- a real `ProjectFile` model
- a first-class current-project owner
- explicit project-owned graph membership separate from runtime/editor/viewer state
- graph-aware spaghetti routing that uses a real current project id

Current runtime still behaves too much like:
- `projectFileId` exists only as routing identity
- spaghetti graph-aware builds still default to `LEGACY_RUNTIME_PROJECT_FILE_ID`
- graph collection reality lives in graph store/runtime structures rather than explicit project ownership
- cached graph entries, editor viewports, and viewer-target state are doing work that project ownership should not depend on

`12A` needs to make the project layer honest before project content tree and cross-graph ownership can grow on top of it.

### Locked Direction

- introduce one first-pass current `ProjectFile`
- keep `12A` in-memory only in first pass
- own current project state in `useAppStore`
- keep graph documents and graph runtime in `useSpaghettiStore`
- make project graph membership explicit and readable at the project layer
- keep `rootAssemblyId` nullable in first pass
- reroute spaghetti graph-aware builds to the real current `projectFileId`
- leave project persistence, project content tree records, and cross-graph rules deferred

### Locked Project Contract

Use this first-pass in-memory project contract:

```ts
type ProjectFile = {
  projectFileId: string
  name: string
  version: number
  graphDocuments: ProjectGraphDocumentEntry[]
  rootAssemblyId: string | null
}

type ProjectGraphDocumentEntry = {
  graphDocumentId: string
  label: string
  sourceFilePath: string | null
  orderIndex: number
}
```

Rules:
- `projectFileId` is the real current project identity
- `name` is project-owned user-facing naming
- `version` exists from the start even though first pass is in-memory only
- `graphDocuments` is the explicit project-owned graph membership collection
- `rootAssemblyId` is a nullable first-pass anchor, not a forced content-tree implementation

Important rule:
- this is the first real `ProjectFile`
- it is not the final project persistence format and not the final project content model

### Locked Ownership Boundary

`useAppStore` owns:
- current `ProjectFile`
- current project id selectors/helpers
- project-owned graph membership and order
- the routing bridge from current project to graph-aware build requests

`useSpaghettiStore` continues to own:
- `GraphDocument` records
- graph-local runtime buckets
- cached graph entries
- editor viewports
- focused/open viewport state
- viewer-target state

Rules:
- a graph can belong to a project even when it is not open in an editor
- project membership must not be reconstructed from viewport focus or viewer-target state
- cached graph lifecycle remains related to graph-document usage, but it is not the same thing as project membership

Plain-English rule:
- the project owns which graphs belong together
- the spaghetti store owns what the app is currently doing with those graphs

### Locked Durable-Versus-Runtime Rule

In first pass, durable-style project truth means:
- `projectFileId`
- project `name`
- project `version`
- graph membership
- graph order
- minimal graph metadata such as label and optional source path
- nullable `rootAssemblyId`

Runtime-only truth remains:
- live graph runtime memory
- accepted build outputs
- graph-owned output surfaces
- dirty cached editor copies
- active/focused editor viewport
- open viewport list
- viewer target / camera / selection / visibility state

Working rule:
- if the data describes what the project is, it belongs in `ProjectFile`
- if the data describes what the app is currently doing with the project, it stays runtime-only

### Locked Routing Rule

After `12A`, graph-aware spaghetti builds should use the real current `ProjectFile.projectFileId`.

Rules:
- `LEGACY_RUNTIME_PROJECT_FILE_ID` remains as legacy fallback for the legacy path and any still-legacy seams
- it should stop being the default for graph-aware spaghetti routing once current project ownership exists
- `buildDispatcher` should continue to consume routed identity without becoming the owner of project state

Practical implication:
- `useAppStore.requestGraphDocumentBuild(...)` should read current project id from app-owned project state
- spaghetti-path routing should no longer pretend every graph-aware build belongs to one fake legacy runtime project

### Implementation Order

1. Add the first `ProjectFile` and `ProjectGraphDocumentEntry` types to the app-owned state surface.
2. Initialize one current in-memory project in `useAppStore`.
3. Populate first-pass project graph membership from the live graph-document collection in spaghetti state.
4. Expose selectors/helpers for:
   - current project
   - current project id
   - current project graph membership
5. Keep graph runtime, cached graph, editor viewport, and viewer-target ownership unchanged in `useSpaghettiStore`.
6. Update graph-aware build request routing to use the current project id.
7. Leave persistence, content tree, and cross-graph behavior out of this phase.

Working sequence rule:
- prefer one honest current-project model over a broad migration
- first pass may mirror existing graph collection rather than redesigning Browser or graph-store data models

### Deferred Out Of `12A`

- project-file disk persistence and load/save UI
- multiple project files
- `Component / Assembly / Object / Part` tree records
- project-local Browser tree rows
- cross-graph `Publish / Receive`
- `Link` versus `Hard Copy`
- reference assets inside project ownership
- final project packaging/export structure

That keeps `12A` from collapsing into:
- `12B` content tree ownership
- `12C` cross-graph ownership rules
- later Browser/workspace and output-structure phases

### Acceptance / Proof Bar

`12A` counts as real only when tests prove:

1. One current in-memory `ProjectFile` exists with the canonical first-pass shape.
2. Project graph membership/order is explicit and readable without reconstructing it from editor viewport state.
3. Creating or loading graph documents updates project graph membership correctly.
4. Duplicating or importing a graph creates a new project graph membership entry correctly.
5. Editor viewport open/focus changes do not redefine project membership.
6. Viewer-target changes do not redefine project membership.
7. Graph-aware build requests use the real current `projectFileId`.
8. `LEGACY_RUNTIME_PROJECT_FILE_ID` is no longer the default for the spaghetti project path.
9. No content-tree ids such as `assemblyId`, `componentId`, `objectId`, or `partId` are required in first pass.

Minimum acceptance statement:
- `12A` is complete only when the app owns a real current `ProjectFile`, graph collection membership is explicit at the project layer, and spaghetti graph-aware routing no longer relies on the fake legacy runtime project id.
