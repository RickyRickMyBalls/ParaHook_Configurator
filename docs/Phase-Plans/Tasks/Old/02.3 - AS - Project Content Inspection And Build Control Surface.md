## Arch Spec

### Spec Target

This implementation target is only:
- `[2.3] AS - Project Content Inspection And Build Control Surface`

This cut intentionally sits:
- after `02.2` made published `Content` structurally honest
- before later Lane `[4]` runtime/build-truth work
- before full `Part` row truth and deeper execution sequencing

Plain-English rule:
- make published `Content` feel like the first honest build/control surface without pretending the deeper runtime is already solved

### Problem Statement

`02.2` made published `Content` structurally honest, but the Browser still needs a calm first execution-facing meaning for those rows.

Without `02.3`, the repo stays stuck between two bad states:
- `Graph Documents` rows carrying too much published build/control meaning
- `Content` rows looking like a second graph list instead of published build targets

`02.3` needs to lock one truthful first-pass Browser behavior where:
- `Graph Documents` remains the authoring/document surface
- `Content` becomes the published build/policy surface
- row click is direct and honest
- build/policy UI stays separate from view UI

### Reasonable Phase Cut

`02.3` should stay small enough to ship as the first honest `Content` build/control layer.

This phase should actually do:
- make `Content` feel different from `Graph Documents`
- make single-click on published `Content` select and rebuild that row scope
- make `Assembly`, `Component`, and `Object` all real build/loading rows
- move graph/source traceability into calmer secondary actions
- keep build/policy controls separate from view controls
- default published `Content` rows to `Live` on load

This phase should not try to solve every later execution-truth question before the Browser has a stable first content build surface.

### Locked Graph Documents Versus Content Surface Rule

In Phase 6:
- `Graph Documents` stays intentionally simple
- `Content` becomes the published build/policy surface

`Graph Documents` rules:
- document-oriented identity only
- open/focus/save/export behavior
- calm document-level state only
- no full published rebuild stack here
- no per-published-row loading bars here

`Content` rules:
- published entity identity
- rebuild interaction
- build/loading presentation
- policy presentation
- source traceability only as secondary actions

### Locked Content Row Interaction Rule

Single-click on published `Content` rows means:
- select that row
- rebuild that row scope

This applies to:
- `Assembly`
- `Component`
- `Object`

Interaction rules:
- this does not redefine graph-document row click behavior
- parent-row rebuild remains selective
- clicking an `Assembly` targets the assembly scope, but only descendants that actually need rebuild work should rebuild
- already-up-to-date descendants should not rebuild just because the parent row was clicked

### Locked Source-Trace Secondary Action Rule

Published `Content` rows keep graph/source traceability, but not in the primary row face.

Primary row language should stay about:
- `Assembly`
- `Component`
- `Object`

Source-trace behavior should live in:
- `View In Graph`
- right-click/context actions
- reveal/highlight behavior
- internal row metadata for later authoring jumps

Reading rule:
- primary row = what published thing is this
- secondary action = where did this come from in authoring

### Locked Assembly / Component / Object Build-State Presentation

In Phase 6:
- `Assembly`, `Component`, and `Object` are all real build/loading rows
- later `Part` truth extends `Object`, not replaces it

First visual treatment:
- `Assembly` gets a dominant aggregate build/loading bar
- `Component` gets a dominant grouped-branch build/loading bar
- `Object` gets a real but slimmer build/loading bar

Presentation rule:
- do not keep `Object` artificially light just because deeper `Part` truth is deferred
- do keep parent rows visually stronger than object rows so the Browser hierarchy stays readable

### Locked Policy Versus View-Control Separation

Published `Content` should default to:
- `Live`

Policy rules:
- build/policy controls stay separate from view controls
- build/generate on-off must not merge with view/show on-off
- the first visible policy control should be an inline row chip on published `Content`

Policy examples:
- `Live`
- later `Release`
- later `Manual`

View examples:
- show/hide
- isolate
- later materials/visibility behavior

### Locked Deferred Later Work

This phase explicitly does not own:
- full `Part` row truth
- revisions/history truth
- later `SEQ / ALL`
- deeper worker/runtime chunk truth
- graph-native worker-contract replacement
- nested assembly/package systems
- richer materials, visibility, and reference workspace behavior
- any later graph-document node-list surface

The handoff rule is:
- `02.3` makes `Content` honest
- later lanes make the deeper runtime final

### Implementation Order

1. Separate graph-document row behavior from published `Content` row behavior so `Graph Documents` remains simple and `Content` becomes the build/policy surface.
2. Implement `Select + Rebuild` semantics for published `Assembly`, `Component`, and `Object` rows while keeping parent rebuild selective.

5. Keep source traceability available through `View In Graph`, right-click, and reveal/highlight actions without letting graph ids dominate the row face.
6. Cover the new row meaning, build presentation, and policy separation with focused Browser/store tests.
