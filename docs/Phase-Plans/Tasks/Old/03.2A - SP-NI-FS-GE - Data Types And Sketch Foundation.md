## Arch Spec

### Spec Target

This implementation target is only:
- `[3.2A] SP / NI / FS / GE - Data Types And Sketch Foundation`

This cut intentionally sits:
- after enough generic node cleanup in `[3.1]` that the node system can host richer geometry contracts
- before the fuller sketch-operation work in `[3.2B]`
- before the first body-feature contracts in `[3.2C]` and `[3.2D]`

### Problem Statement

The foundational geometry lane now has a clearer planning shape, but the first type vocabulary and graph-facing `Sketch` shell are still under-specified against the current codebase.

Without this cut:
- later sketch-operation work has no stable node shell to plug into
- `Extrude` has no honest `SketchProfile` target contract
- implementers would still need to invent how `Sketch` fits into the present node registry, view-model, evaluator, and viewport overlay seams

### Locked First-Pass Win

`[3.2A]` counts as real when:
- the first geometry-authoring type vocabulary is explicit and small
- `Geometry/Sketch` exists as a real node type instead of only planning text
- the node has a dedicated `sketch` shell template instead of pretending the generic node or part template is enough
- the node evaluates `SketchProfiles` and `SketchProfile` from one managed `SketchFeature` payload
- the node can enter a viewer-side plane-pick flow for `SketchPlane`
- downstream phases can honestly target `SketchProfiles` and `SketchProfile`

Plain-English rule:
- make the language and shell real before making the sketch feature rich

### Locked Node Identity And Host Model

The first graph-native geometry family should use:
- `Geometry/*`

This phase introduces:
- `Geometry/Sketch`

Implementation rule:
- `Geometry/Sketch` is a first-class graph node, not a part-node wrapper
- `Geometry/Sketch` uses a dedicated `template: 'sketch'`
- `Geometry/Sketch` does not reuse the `part` template
- `Geometry/Sketch` does not hide inside a broader part `FeatureStackView`

Node-owned source of truth:
- the node stores one managed `SketchFeature` object in node params
- that managed `SketchFeature` is the only persisted source of truth for:
  - `plane`
  - `components`
  - derived `outputs.profiles`
  - `uiState`
- this phase does not introduce a full node-local `FeatureStack`

### Locked Stored Payload And Evaluation Model

`Geometry/Sketch` params should store one managed `SketchFeature` payload with at least:
- `type: 'sketch'`
- `featureId`
- `plane`
- `components`
- `outputs.profiles`
- optional `outputs.diagnostics`
- `uiState`

Implementation rule:
- `[3.2A]` reuses the existing standalone `SketchFeature` schema and data model from:
  - `src/app/spaghetti/features/featureTypes.ts`
  - `src/app/spaghetti/features/featureSchema.ts`
- `[3.2A]` derives profile outputs through `deriveProfilesWithDiagnostics`
- `[3.2A]` does not introduce a second geometry engine path

Evaluation boundary:
- `[3.2A]` is schema + evaluator + node-shell + viewer-session work
- `compileGraph.ts` remains explicitly out of scope in this phase
- worker build/runtime geometry execution remains explicitly out of scope in this phase

Non-goal rule:
- if a required change exists only to make `Geometry/Sketch` participate in build compilation, it belongs to a later phase, not `[3.2A]`

### Locked First `Sketch` Hierarchy In This Phase

```text

|- Draw/Edit Curves Inside
|- Close/Select Profile
`- Outputs
```

But this phase only owns the shell and empty body shape:

```text
Sketch

|  `- Empty internal authoring surface in [3.2A]
|- Close/Select Profile
|  `- Deferred to [3.2B]

   `- SketchProfile : [SketchProfile]
```

Phase-boundary rule:
- `[3.2A]` makes the node body and shell real
- `[3.2B]` fills that body with actual line/arc/spline authoring plus close/select profile behavior

### Locked `SketchPlane` Row Shape And Behavior

The `Inputs` section should start as explicit rows, not a loose parameter block:

```text
Sketch
`- Inputs
   `- SketchPlane row
      |- input pin: [Plane]
      |- label: SketchPlane
      |- value: local plane or wired plane
      `- action: +  (start plane pick)
```

First input-row behavior:
- the row keeps a normal graph input pin so an upstream plane can be wired into it from the canvas
- the node persists one local plane assignment for fallback
- the row-level `+` is the primary first-pass way to assign the local plane
- if a plane is wired into the input pin, that wired plane is authoritative for display and evaluation while connected
- the wired plane must not erase the stored local plane fallback
- clicking `+` should collapse/minimize the broader spaghetti editor
- the viewer should enter plane-pick mode for this sketch through lightweight store session state
- the viewer plane-pick UI should be hosted through `ViewportOverlay`
- the first options shown in the viewer should be ghost preview planes/grids around the origin for:
  - `XY`
  - `XZ`
  - `YZ`
- choosing one of those previews assigns the local `SketchPlane` value and returns the user to the normal `Sketch` node/editor state

Deferred from this first row flow:
- clicking arbitrary planar faces
- custom offset/work planes
- richer plane history/management UI

### Locked Geometry Data Types

Lock these first-class graph-facing kinds now:
- `number`
- `boolean`
- `vec2`
- `plane`
- `sketchProfiles`
- `sketchProfile`
- `solidBody`

Keep these deferred or thin in this phase:
- `vec3`
- `transform2d`
- `sketchCurve`
- `sketchCurveRef`

Explicit first-pass rule:
- `SketchCurves` is not part of the shipped `[3.2A]` contract
- if the code later needs curve exposure, that belongs in a later phase instead of being smuggled into this cut

Reason:
- the current graph/runtime already has real primitive transport for numbers, booleans, and `vec2`
- the current sketch feature substrate already makes plane assignment and resolved profile output honest seams
- explicit curve objects, curve refs, and transform-placement contracts are not yet graph-native surfaces the current code honestly depends on

### Locked First Honest `Geometry/Sketch` Shell Pins

Lock the first shipped shell as:
- `in:SketchPlane - [Plane]`
- `out:SketchProfiles - [SketchProfiles]`
- `out:SketchProfile - [SketchProfile]`

Explicitly defer from the shell:
- `out:SketchCurves`
- `in:SketchPlace - [Transform2D]`

Rule:
- ship the smallest shell that can feed downstream `Extrude` work without forcing speculative placement or curve-reference contracts

### Locked Output Semantics

`SketchProfiles` behavior:
- emit all resolved profiles derived from the managed `SketchFeature.components`

`SketchProfile` behavior:
- emit one selected-style profile only when exactly one resolved profile exists
- emit `null` when zero resolved profiles exist
- emit `null` when multiple resolved profiles exist

Reason:
- `[3.2A]` must stay honest before `[3.2B]` adds `Close / Select Profile`
- the phase should not pretend profile selection already exists by auto-picking the first profile in a multi-profile sketch

### Locked Shell Boundary

Define what belongs in this phase:

- shell inputs/outputs
- first input-row interaction for `SketchPlane`
- editor collapse/minimize handoff into viewer plane-pick mode
- empty internal authoring surface
- evaluator-level profile output derivation

Explicitly defer:
- draw/edit curve operations
- close/select profile operations
- arbitrary face-picked plane creation
- builder UX polish

Body ownership rule:
- `Draw/Edit Curves Inside` renders as a placeholder/empty authoring body owned by the `sketch` template

## Implementation Order

1. Extend the graph type vocabulary with `plane`, `sketchProfiles`, `sketchProfile`, and `solidBody`.
2. Add the `Geometry/*` node family entry seam and register `Geometry/Sketch`.
3. Store one managed `SketchFeature` payload in `Geometry/Sketch` params and make it round-trip through schema parsing.
4. Add evaluator support for deriving `SketchProfiles` and only-single `SketchProfile` from the managed `SketchFeature`.
5. Add a dedicated `sketch` template path in registry, node VM selection, and node rendering.
6. Render the `SketchPlane` input row plus an empty internal authoring placeholder and deferred review row.
7. Add lightweight sketch-plane pick session state in the store and host the ghost preview picker in `ViewportOverlay`.
8. Add tests for port-kind validation, params round-tripping, profile output semantics, wired-plane precedence, and plane-pick mode entry/exit.

## Acceptance Criteria

- `Geometry/Sketch` exists as a real user-facing node type
- `Geometry/Sketch` uses a dedicated `sketch` template instead of the `part` template or generic fallback only
- the node stores one managed `SketchFeature` payload in params
- `SketchPlane` appears as a dedicated input row with both a graph input pin and a right-side `+` action
- clicking `+` enters viewer-side plane-pick mode through lightweight store session state and `ViewportOverlay`
- plane-pick mode shows only `XY`, `XZ`, and `YZ` ghost plane/grid previews around the origin
- confirming a plane pick writes the local `SketchPlane` value and returns the user to the normal node/editor state
- a wired `SketchPlane` overrides local display/evaluation while connected without deleting the local fallback value
- empty sketch data yields `SketchProfiles = []` and `SketchProfile = null`
- one valid closed profile yields one `SketchProfiles` entry and one `SketchProfile`
- multiple valid profiles yield populated `SketchProfiles` and `SketchProfile = null`
- the node body shows an explicit empty authoring placeholder and does not yet expose draw/review tools
- `[3.2A]` does not require `compileGraph.ts` or worker runtime changes to count as complete
