# 01.5 - Multiple Spaghetti Bowls

## Doc History
1. 2026-03-06 16:02: Created this doc as the master planning note for the future multi-graph Spaghetti system, covering graph/document ownership, worker routing, UI structure, identity rules, and the guardrails current ParaHook work should follow before the feature exists

## Purpose

This file is the master plan for the future multi-graph Spaghetti editor.

`Multiple Spaghetti Bowls` means:
- more than one graph loaded at once
- more than one graph visible in the product at once
- more than one graph contributing outputs into the shared preview/viewer system

This is a future feature.
But it is important enough that the current app should avoid choices that would make it painful later.

## Big Idea

Today, the app mostly behaves like there is one active Spaghetti graph.

Long-term, the app should be able to support:
- multiple graph files loaded at once
- multiple editor instances
- one graph in a floating window and one graph in a browser window
- multiple independent outputs rendered into the same shared viewer

In that future, the user is not just editing one graph.
The user is managing multiple graph documents at the same time.

## What A Multi-Graph Spaghetti System Means

The core change is:

- graph becomes a first-class top-level document

instead of:

- one hidden singleton graph living inside app state

That means the app eventually needs to think in terms of:

- `graphId`
- graph document
- graph compile state
- graph build state
- graph preview state
- graph debug state
- editor instance state

## Main User Experience

The future multi-graph experience should probably feel like:

- the user can load or create multiple graph files
- each graph appears as its own item in a `Graphs` panel
- each graph can be opened in one or more editor windows
- each graph can output parts into the shared viewport
- the user can inspect parts within each graph separately
- the user can show/hide or focus graphs and parts independently

So the rough UI hierarchy becomes:

- `Graphs`
  - `Graph A`
    - `Parts`
    - `Preview`
    - `Build Status`
    - `Debug`
  - `Graph B`
    - `Parts`
    - `Preview`
    - `Build Status`
    - `Debug`

This means the old flat `Parts List` will likely become a subsection of a larger graph-aware panel.

## Architectural Changes Needed

### 1. Graph Document Model

Each graph needs to become a real document with:

- `graphId`
- graph metadata
- nodes
- edges
- graph-local settings
- graph-local compile/build/debug derived state

This is the first big requirement.

Without a real graph-document concept, multi-graph support becomes a pile of special cases.

### 2. Graph State Versus Window State

The app must separate:

- graph state
- editor window state

Graph state is shared truth.
Window state is local UI state.

Graph state includes:
- nodes
- wires
- params
- compile outputs
- artifacts
- OutputPreview mapping

Window/editor-instance state includes:
- selected node
- pan/zoom
- open debug drawer
- window size/mode
- which graph that editor is currently showing

### 3. Worker Ownership Per Graph

Build and compile work needs to become graph-aware.

That means:
- build requests must include `graphId`
- latest-only behavior should happen per graph
- stale-drop behavior should happen per graph
- worker responses must be routed back to the correct graph document

Without that, one graph can easily stomp another graph’s build state.

### 4. Graph-Aware Identity

The current app already separates preview identity from build identity.

In a multi-graph future, identity needs one more layer:

- `graphId + slotId`
- `graphId + viewerKey`
- `graphId + partKeyStr`
- `graphId + nodeId`

That way:
- two different graphs can both contain a `Cube`
- two different graphs can both have a slot `slot-1`
- two different graphs can both emit a similar part

without collisions.

### 5. Shared Viewer Composition

The viewer eventually needs to render outputs from multiple graphs at once.

That means the viewer path should evolve from:

- one graph -> one preview path

to:

- graph A -> preview rows
- graph B -> preview rows
- graph C -> preview rows
- composition layer -> final viewer inputs

The viewer should still stay render-only.
It just needs a graph-aware composition layer above it.

### 6. Graph-Level Debug

DBG will also need a graph-aware future.

That means:
- compile inspector per graph
- artifact inspector per graph
- OutputPreview inspector per graph
- Preview VM inspector per graph
- Viewer input inspector that still lets the user understand which graph a rendered item came from

## Proposed Future UI Shape

### Graphs Panel

The future replacement for a flat part list is probably:

- `Graphs Panel`

with nested structure like:

- `Graph A`
  - `Parts`
  - `Preview`
  - `Build`
  - `Debug`
- `Graph B`
  - `Parts`
  - `Preview`
  - `Build`
  - `Debug`

This gives the user one top-level place to understand:
- which graphs are loaded
- what each graph produced
- what each graph is previewing
- which graph has problems

### Editor Windows

Editor windows should eventually become graph viewers/editors, not graph owners.

That means:
- one window can point at Graph A
- another window can point at Graph B
- two windows could even point at the same graph if desired later

### Shared Viewport

The shared viewport should show outputs from one or more graphs while keeping:
- graph identity
- part identity
- preview identity

explicit.

## Recommended Moving-Forward Rules

These are the practical rules to follow now, before the feature exists.

- Treat graph as the real top-level authored document.
- Avoid new singleton assumptions when adding Spaghetti features.
- Keep graph-owned state separate from panel/window-owned state.
- Keep build outputs and preview outputs derived from graph state.
- Keep all identities stable and explicit.
- Prefer selectors/helpers that can later be keyed by `graphId`.
- Do not hide graph identity inside UI-only assumptions.
- Avoid designing the part list as if there can only ever be one graph.
- Avoid viewer logic that assumes only one preview source exists.
- Avoid worker/build state that assumes only one active build stream exists.

## Things To Watch For In Current Work

If any new work introduces these assumptions, it may cause future pain:

- one global current graph forever
- one global compile result forever
- one global preview VM forever
- one flat global part list forever
- one active editor window forever
- graph state mixed directly into floating-window state

Those choices are not always wrong short-term, but they should be made carefully and isolated where possible.

## Suggested Phased Implementation Later

This should probably be built in stages, not all at once.

### Stage 1 - Graph-Aware Internals

- introduce `graphId`
- separate graph document state from editor-instance state
- key compile/build/debug outputs by graph

### Stage 2 - Graphs Panel

- replace the flat part list with a graph-aware panel
- show parts nested under graphs
- show build/debug status per graph

### Stage 3 - Multi-Graph Viewer Composition

- let more than one graph feed the shared viewport
- make visibility/focus graph-aware
- keep preview/build identity explicit

### Stage 4 - Multi-Window Editing

- allow multiple editor windows/hosts
- allow floating and browser-window hosts
- connect windows to graph documents cleanly

## Summary

`Multiple Spaghetti Bowls` is really the future multi-graph document system.

The most important long-term move is:
- graph becomes the main ownership unit

Once that is true, the rest can follow:
- graph-aware parts
- graph-aware preview
- graph-aware debug
- graph-aware viewer composition
- multiple editor instances over shared graph documents

## Phase Plan

This feature should be built in phases.

The goal is not to ship multi-graph all at once.
The goal is to make the app more graph-aware in layers until multi-graph behavior becomes natural.

### `SP-7` Graph Document Foundations

Purpose:
- make graph a first-class document instead of a hidden singleton

Main work:
- introduce stable `graphId`
- define graph-document ownership boundaries
- separate graph state from editor-window state
- make compile/build/debug state graph-aware

### `SP-8` Graph-Aware Worker And Preview Routing

Purpose:
- make the build and preview pipeline safe for more than one graph

Main work:
- key build requests and results by `graphId`
- make latest-only and stale-drop happen per graph
- make OutputPreview / preview VM / viewer inputs graph-aware
- harden graph-aware identity rules

### `SP-9` Graphs Panel And Nested Parts

Purpose:
- replace the old flat single-graph mental model in the UI

Main work:
- create a `Graphs` panel
- nest `Parts`, `Preview`, `Build`, and `Debug` under each graph
- support graph-level visibility, focus, and inspection

### `SP-10` Shared Viewport Composition

Purpose:
- let multiple graphs contribute outputs into one shared viewport

Main work:
- compose preview rows from multiple graphs
- keep graph identity visible in the viewer path
- support graph-aware visibility and highlighting

### `SP-11` Multi-Window Graph Editing

Purpose:
- allow multiple editor hosts to work over graph documents

Main work:
- support one graph per window/host
- support floating and browser-window hosts
- keep editor-instance UI state separate from graph truth

### `SP-12` Multi-Graph Debug And Polish

Purpose:
- make the system understandable once many graphs exist at once

Main work:
- graph-aware debug inspectors
- graph-aware status/read-model cleanup
- graph-aware selection and focus polish
- final UX hardening for large multi-graph sessions
