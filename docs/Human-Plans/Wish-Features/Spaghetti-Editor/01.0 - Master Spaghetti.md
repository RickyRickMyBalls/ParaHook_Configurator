Use this file to answer:
- what Spaghetti currently is

- what belongs to one graph

This is not a task file.
It is the high-level map of the Spaghetti system.

## What Spaghetti Is

Spaghetti is the advanced authoring system inside ParaHook.

It is the place where:
- graphs are created
- nodes are placed
- wires are connected
- part systems are defined
- drivers and params are routed
- Feature Stack data is authored inside part nodes
- OutputPreview determines what should be previewed

Right now, the app mostly behaves like one active Spaghetti graph exists at a time.

Long-term, Spaghetti should be able to support:
- multiple graphs
- multiple editor instances
- multiple graph files loaded at once
- shared viewport composition across outputs from different graphs

## The Main Layers Inside Spaghetti

### Graph

A graph is the top-level authored document.

A graph contains:
- nodes
- edges / wires
- graph-level metadata
- compile output derived from the graph
- OutputPreview mapping derived from the graph
- debug state derived from the graph

Future rule:
- graph should become the main ownership unit for Spaghetti
- not just the current invisible singleton state

### Nodes

Nodes are the boxes on the canvas.

A node has:
- identity
- type
- params
- inputs
- outputs
- UI position/state

Some nodes define real parts.
Some define values or drivers.
Some define system behavior like preview routing.

### Wires

Wires connect node outputs to node inputs.

Wires are how values and relationships move through the graph.

Long-term, wires should increasingly carry:
- typed values
- typed grouped values
- typed custom objects

not only loose ad hoc UI params.

### Part Nodes

Part nodes are the main geometry-producing nodes.

Current relevant part nodes include:
- `Part/Baseplate`
- `Part/ToeHook`
- `Part/HeelKick`
- `Part/Cube`
- `Part/CubeProof`

Part nodes:
- own part-specific params
- contain Feature Stack data
- compile toward deterministic artifacts
- eventually become previewable/renderable parts

### Driver / Param / Input Nodes

These nodes represent editable values and control sources.

Current relevant families include:
- `Param/Number`
- `Param/Boolean`
- `Param/Vec2`
- older `Primitive/*` compatibility-style nodes
- utility nodes used to adapt or pass values through

Long-term, this area should grow into a cleaner driver system with:
- canonical control identity
- typed values
- grouped values
- equation-ready behavior

### Feature Stack

Feature Stack remains internal to part nodes.

It is not a nested graph.

Feature Stack currently includes:
- `sketch`
- `extrude`

Long-term it may expand to:
- `fillet`
- `chamfer`
- `boolean`
- `pattern`
- `mirror`

### OutputPreview

`System/OutputPreview` is the current preview-routing system.

It defines which graph-produced parts flow into the preview pipeline.

Important architecture rule:
- preview identity is separate from build identity

That separation should remain true even in a future multi-graph system.

## Things Inside One Graph

Inside one graph, the important concepts are:

- graph document
- nodes
- wires
- drivers / params / inputs
- part nodes
- Feature Stack data inside part nodes
- OutputPreview node and slots
- compile output
- artifacts
- preview VM
- debug visibility for that graph

So the correct mental model is:

- graph at the top
- nodes and wires inside the graph
- parts and drivers defined by nodes
- compile/build/preview derived from that graph

## Things The User Can Currently Spawn On The Canvas

The exact list can evolve, but the main current spawnable directions are:

- part nodes
  - `Part/Baseplate`
  - `Part/ToeHook`
  - `Part/HeelKick`
  - `Part/Cube`
  - `Part/CubeProof`
- system nodes
  - `System/OutputPreview`
- param/input/value nodes
  - `Param/Number`
  - `Param/Boolean`
  - `Param/Vec2`
- some primitive/utility/helper nodes, depending on current registry visibility rules

Long-term, the canvas should probably expose a cleaner palette around:
- parts
- drivers
- params
- system nodes
- utility nodes

## Multi-Graph Direction

If Spaghetti becomes a real multi-graph system, the app should stop thinking in terms of one global graph.

Instead, it should think in terms of:

- `graphId`
- graph document state
- graph-specific compile/build state
- graph-specific preview state
- graph-specific debug state

That means each loaded graph file should become its own first-class document.

## What A Multi-Graph System Would Need

### 1. Graph Document Ownership

Each graph should have:
- a stable `graphId`
- its own nodes and edges
- its own compile output
- its own build outputs
- its own OutputPreview mapping
- its own debug inspection state

### 2. Editor Instance Ownership

Editor windows should not own the graph itself.

Each open editor instance should have:
- an `instanceId`
- a linked `graphId`
- per-instance UI state like:
  - pan/zoom
  - selected node
  - debug drawer visibility
  - window size/mode

### 3. Worker Build Ownership Per Graph

The worker/build path should become graph-aware.

That means:
- build requests should include `graphId`
- stale-drop and latest-only should happen per graph
- results should come back tagged to the correct graph

### 4. Graph-Aware Identity

When multiple graphs are loaded, identity needs one more level.

Examples:
- `graphId + slotId`
- `graphId + viewerKey`
- `graphId + partKeyStr`

Without this, two graphs that both produce similar parts can collide in preview and viewer state.

### 5. Graphs Panel Instead Of One Flat Part List

If many graphs can be loaded at once, a flat Part List will not be enough.

A better long-term shape is:

- `Graphs`
  - `Graph A`
    - `Parts`
    - `Preview`
    - `Build Status`
  - `Graph B`
    - `Parts`
    - `Preview`
    - `Build Status`

So yes:
- the Part List probably becomes a subsection under a larger `Graphs` panel

### 6. Shared Viewport Composition

The viewer should eventually be able to compose outputs from:
- Graph A
- Graph B
- Graph C

without confusing their identities or debug paths.

## Rules To Follow Now So Multi-Graph Is Easier Later

- Treat graph as the real top-level authored document.
- Avoid singleton assumptions where possible.
- Keep graph state separate from editor-window UI state.
- Keep compile/build state derived from graph state.
- Keep preview/build identity explicit and stable.
- Add graph-aware identity when future systems need it.
- Do not let the viewer become the owner of graph truth.
- Do not let editor windows own product truth.
- Prefer reusable selector/read-model layers over one-off UI derivations.

## Summary

Spaghetti should be understood as a graph-authoring system first, not just a single editor window.

Today it is mostly one graph in one active app context.
Tomorrow it should be able to become:
- many graphs
- many editor instances
- many outputs
- one shared deterministic build and preview architecture
