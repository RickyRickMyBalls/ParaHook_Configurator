### Purpose:

This file is a future-feature wishlist for the Spaghetti Editor.

It is not a task file.
It is not a changelog.
It is a place to capture the future direction for the Spaghetti Editor so the ideas do not get lost.

## Current Window / Layout Pain Points

Known issues worth fixing:

1. The Spaghetti Editor toolbar drag bar cannot move high enough.
   - There is likely a min-height or layout clamp blocking it.

2. The Spaghetti Editor toolbar drag bar should sit directly above the canvas window.
   - It should clearly represent the real boundary between toolbar/header content and canvas content.
   - Some controls may need to move if they are currently owned by the wrong region.

3. The Debug Inspector drag bar can get stuck.
   - The canvas min-height or panel split rules are likely still constraining it incorrectly.

## Spaghetti Window Modes

The Spaghetti Editor should eventually support four window modes:

1. Toolbar
2. Half Screen
3. Full Screen
4. New Browser Window

### Toolbar Mode

- Compact utility mode
- Width should match the ParaHook Generator title block region on the top left
- Best for quick edits and monitoring

### Half Screen Mode

- Mid-size working mode
- Leaves a meaningful amount of viewport visible

### Full Screen Mode

- Largest in-app editing mode
- Makes the Spaghetti Editor the primary working surface

### New Browser Window

- Opens the editor in a separate browser window
- Should always be available as an option

## Window Controls

Desired control model:

- Browser Window button is always visible at the top right
- Two additional mode buttons appear for the in-app modes that are not currently active

Examples:

- If current mode is Toolbar:
  - show Half Screen
  - show Full Screen

- If current mode is Half Screen:
  - show Toolbar
  - show Full Screen

- If current mode is Full Screen:
  - show Toolbar
  - show Half Screen

This keeps the controls compact and avoids showing a button for the already-active mode.

## Ownership Model For Windowing

Recommended long-term ownership split:

- `AppShell`
  - owns outer window mode
  - owns floating window geometry
  - owns browser-window launching

- `SpaghettiPanel`
  - owns header vs canvas split
  - owns canvas vs debug split
  - owns panel-local resize behavior

This keeps global windowing separate from panel-internal layout.

## Browser Window Support

Opening the Spaghetti Editor in a new browser window is possible, but it should not be treated as a small cosmetic change.

The real challenge is not `window.open(...)`.
The real challenge is state ownership and synchronization.

Questions a browser-window mode must answer:

- Does the browser window edit the same graph as the main app?
- Is the window editing a shared live document or a copied snapshot?
- How does compile/build state stay in sync?
- How does selection/UI state stay local to each window?

## Multiple Spaghetti Editor Instances

Long-term, the user should be able to open multiple Spaghetti Editor instances.

Possible combinations:

- two floating windows
- one floating window and one browser window
- two browser windows

These instances might:

- edit the same graph/document
- edit different graphs/documents

Those are very different use cases and should be planned separately.

## Multiple Independent ParaHooks

A major future goal is:

The user can build two different ParaHooks at the same time, each from its own Spaghetti Editor instance, while sharing the same viewport.

That means the app needs to support more than one active Spaghetti document.

This is bigger than just adding another floating window.

## Architecture Needed For Multi-Instance / Multi-Document

To support multiple independent Spaghetti editors cleanly, the app should eventually separate:

1. Document state
2. Editor instance state
3. Window host state
4. Shared viewport composition

### Document State

Each document should have a `documentId`.

A document should own:

- graph
- compile result
- build outputs
- OutputPreview state
- preview/debug data derived from that document

This allows two different ParaHooks to exist independently.

### Editor Instance State

Each editor surface should have an `instanceId`.

An editor instance should own:

- selected node
- pan/zoom
- section collapse state
- debug drawer visibility
- local window mode
- local position and size if floating

An editor instance should point to a `documentId`.

### Window Host State

The app should have a window-manager concept that can host editor instances in different containers:

- floating in-app window
- browser popup window

The host is not the document.
The host is just where the editor instance is shown.

### Shared Viewport Composition

If two independent ParaHooks share one viewport, the viewport must compose outputs from multiple documents.

That means renderable entries need document-scoped identity.

## Identity Requirements

To avoid collisions, the app will eventually need identity at two levels:

### Document / build identity

- `documentId`
- `nodeId`
- `partKey`
- `partKeyStr`

### View / preview identity

- `documentId`
- `slotId`
- `viewerKey`

Without `documentId`, two different documents both rendering a `cube` will collide.

## Build Pipeline Requirements

For multi-document support, compile/build should be owned per document, not per visible window.

That means:

- compile belongs to the document
- build outputs belong to the document
- preview VM belongs to the document
- debug VM belongs to the document

Two windows showing the same document should not cause two unrelated builds.

Two windows showing different documents should not overwrite each other's build results.

## Cross-Window Sync

If browser windows are involved, the app will need a synchronization model.

Possible options:

- `BroadcastChannel`
- shared persisted store with sync events
- a dedicated window-manager/sync layer

The important rule is:

window state should be per instance,
document state should be shared by document.

## Suggested Long-Term Building Blocks

Probable future architecture:

- `SpaghettiDocumentStore`
- `SpaghettiEditorInstanceStore`
- `SpaghettiWindowManager`
- per-document compile/build ownership
- multi-document viewport composition layer

## Short Summary

Future Spaghetti Editor direction includes:

- fixing the current drag-bar and panel split bugs
- adding Toolbar / Half Screen / Full Screen window modes
- adding a Browser Window mode
- supporting multiple editor instances
- supporting multiple independent ParaHook documents
- eventually rendering multiple Spaghetti-driven outputs into one shared viewport

This is likely a multi-phase architecture track, not a single feature.
