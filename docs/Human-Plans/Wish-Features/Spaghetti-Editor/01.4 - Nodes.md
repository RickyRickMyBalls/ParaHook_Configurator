# 01.4 - Nodes

## Purpose

This doc explains what nodes currently are in the Spaghetti Editor.

It is meant to answer:
- what a node actually is
- what kinds of nodes exist right now
- how nodes relate to parts, values, system behavior, and preview

## Plain-English Explanation

A node is one box in the Spaghetti Editor graph.

Each node is a small self-contained unit with:
- an identity
- a type
- some internal parameters
- input ports
- output ports
- optional UI state like position and collapsed mode

So in plain English, a node is not "the geometry itself."

A node is more like:
- a part definition
- a value source
- a system tool
- or a utility/helper box

The graph stores many of these nodes and the wires between them.

## What Nodes Are Made Of

At the schema level, a node is simple.

It has:
- `nodeId`
- `type`
- `params`
- optional `partSlots`
- optional `ui`

That means the raw graph only stores the instance data.

The deeper meaning of the node comes from the node registry, where each node type defines:
- label
- params schema
- default params
- input ports
- output ports
- compute behavior
- UI sections
- driver behavior

So the graph stores "this node exists here," and the registry explains "what this node means."

## Current Node Families

Right now the nodes in Spaghetti fall into a few main groups.

### Part Nodes

These are the nodes that can become actual built parts.

Current examples:
- `Part/Baseplate`
- `Part/Cube`
- `Part/CubeProof`
- `Part/ToeHook`
- `Part/HeelKick`

These are the most important nodes because they can feed the build pipeline and eventually produce `PartArtifact`s.

### System Nodes

These control graph/system behavior rather than creating geometry directly.

Current example:
- `System/OutputPreview`

This kind of node is about preview routing and system behavior, not raw geometry creation.

### Param Nodes

These are explicit authored value nodes.

Current examples:
- `Param/Number`
- `Param/Boolean`
- `Param/Vec2`

These act like clean value sources that can feed other nodes.

### Primitive Nodes

These are lower-level helper/value nodes.

Current examples:
- `Primitive/Number`
- `Primitive/Vec2`
- `Primitive/SplineFromPoints`

These look like lower-level or compatibility-era building blocks.

### Utility Nodes

These are helper or pass-through nodes.

Current examples:
- `Utility/IdentitySpline2`
- `Utility/IdentityNumberMm`

These are usually adapters or simple identity-style helpers.

## Important Rule For Part Nodes

Part nodes are still one node even when they contain a lot of internal data.

For example, a part node may contain:
- Feature Stack data
- section layout
- driver metadata
- inputs and outputs

But it is still one graph node.

This matters because:
- a part node is not a nested mini-graph
- Feature Stack data stays internal to the part node
- the graph does not treat each feature as a separate graph node

## What Nodes Do At Runtime

At runtime, nodes participate in evaluation.

The rough flow is:
- nodes exist in the graph
- the registry defines what each node type means
- graph evaluation resolves inputs
- node logic computes outputs
- part nodes may compile into build inputs or Feature Stack IR
- system nodes like `OutputPreview` help route preview behavior

So a node is both:
- a graph object
- and a typed behavior defined by the registry

## How Nodes Relate To Preview

Not all nodes are about rendering directly.

Some nodes:
- provide values
- shape part definitions
- control system behavior

The preview path is more specific:
- part nodes can contribute built outputs
- `OutputPreview` maps those outputs into slots
- selectors then build preview rows and viewer parts

So nodes participate in the render pipeline, but not every node is itself a renderable thing.

## The Most Important Mental Model

The shortest useful mental model is:

- a node is one typed box in the graph
- the graph stores the node instance
- the registry defines what the node is
- edges connect node outputs to node inputs
- some nodes produce values
- some nodes produce parts
- some nodes control system behavior

## Technical Examples

### Example: Basic Node Shape

```ts
type SpaghettiNode = {
  nodeId: string
  type: string
  params: Record<string, unknown>
  partSlots?: PartSlots
  ui?: NodeUI
}
```

### Example: Number Param Node

```ts
{
  nodeId: "node-1",
  type: "Param/Number",
  params: {
    value: 42
  }
}
```

### Example: Cube Part Node

```ts
{
  nodeId: "node-cube",
  type: "Part/Cube",
  params: {
    featureStack: { ... }
  },
  ui: {
    x: 240,
    y: 120
  }
}
```

### Example: OutputPreview Node

```ts
{
  nodeId: "node-preview",
  type: "System/OutputPreview",
  params: {
    slots: [{ slotId: "s001" }],
    nextSlotIndex: 2
  }
}
```

### Example: Edge Between Nodes

```ts
{
  edgeId: "edge-1",
  from: {
    nodeId: "node-1",
    portId: "value"
  },
  to: {
    nodeId: "node-cube",
    portId: "someInput"
  }
}
```

## Current Architectural Takeaway

Nodes are the basic typed units of the Spaghetti system.

The important split is:
- the graph stores node instances
- the registry defines node meaning
- evaluation/compile logic determines what node outputs mean
- part nodes may eventually become built parts
- system nodes like `OutputPreview` control preview routing instead of generating geometry
