## Doc Body

### Family Phase Goal

`Catalog-Gen2-5` should let Catalog carry pre-built PubWheel starting assemblies as first-class starting records, not as ordinary part cards.

A starting assembly is a known whole-build entry the user can choose before making swaps. It may be backed by a repo-owned source asset later, preferably `.step` or `.stp` for user-supplied repo-backed assets, but the catalog record itself must still say whether the load behavior is available now or only planned for a later owner.

### Boundary Rules

- A pre-built PubWheel entry is not a loose part listing.
- Do not add fake assembly records that imply a complete source asset exists when it does not.
- Do not treat PubParts external-linked records as local assembly files.
- Do not consume loose XR/ADV STEP assets until `Catalog-Gen2-4.5` classifies them as complete assembly-ready assets.
- Keep `.step` and `.stp` as the preferred repo-backed source format when assets are supplied.
- Keep preview media separate from source geometry.
- Do not ship the full builder or compatibility checker in this family phase.
- If a load-as-starting-configuration action is not wired to a downstream owner, it must be marked planned or unavailable instead of pretending to run.
- Do not use Catalog to solve STEP import fidelity; `Import-5 - STEP Import Metadata, Units, And Loader Fidelity` owns STEP units, tessellation/quality, heavy-load progress, parse reuse, and loader-parameter truth.

### Current Live Read

Current Catalog contract seams:
- `CatalogItemRecord.assetKind` currently supports `reference-asset` and `environment`.
- `CatalogItemRecord.actionKind` currently supports `load-preview`, `add-to-project`, and `apply-environment`.
- `sourceKind` currently supports `repo`, `imports`, and `external`.
- external PubParts entries are source-linked and do not have local `assetPath` behavior.
- repo-backed preview resolution already recognizes `.step` along with mesh formats for reference previews.
- Phase 1 added a distinct optional `itemRole: 'starting-assembly'` catalog read seam.
- there is no load-as-starting-configuration action owner yet.

Current planning seams:
- `Catalog-Gen2-4.5` owns user-supplied repo-backed XR/ADV asset folder intake.
- `.step` and `.stp` are preferred for repo-backed source assets.
- `public/Catalog/boards/adv/ADV_Full Assembly_parts.step` exists as one repo-backed ADV assembly-shaped STEP source file; it is large at about 55.8 MB, and no matching assembly/board preview asset was found during Phase 2 prep.
- `public/Catalog/assemblies/xr/Assembly_XR_Pubwheel_1.step` and `public/Catalog/assemblies/xr/Assembly_XR_Pubwheel_1.glb` now exist as supplied XR PubWheel full-assembly source candidates; they are one `pubwheel_1` item/version pair, not two Catalog entries.
- `Catalog-Gen2-4.5 / Phase 1` defined the versioned multi-file source asset-set contract and `Catalog-Gen2-4.5 / Phase 2` migrated the XR planned source into `sourceAssetSet` with `pubwheel_1` / `v1`, keeping STEP as preferred source and GLB as companion mesh under one item.
- `Import-5 - STEP Import Metadata, Units, And Loader Fidelity` owns the actual STEP import hardening lane, including units truth, mesh versus B-Rep honesty, quality controls, large-file load/progress, and parse reuse.
- `Catalog-Gen2-5` may consume only complete assembly-ready assets after classification, not loose parts.

### Acceptance Read

This family phase is complete when:
- Catalog can distinguish starting assemblies from loose parts in its contract and UI read
- the main platform family starting assembly entries are represented honestly
- unavailable or planned load behavior is visible and does not pretend to be implemented
- repo, imports, and external source lanes remain distinct
- STEP source preference for repo-backed assembly assets is preserved in docs and metadata expectations
- every Gen2 HLG/CLG owned by this family phase is either checked off with code/docs proof or routed to a follow-up phase

## [x] `Catalog-Gen2-5 / Phase 1` - `Starting Assembly Contract And Boundary`

### Phase 1 Summary

#### Purpose

Define and implement the smallest Catalog contract/read that marks an item as a starting assembly instead of a loose part listing.

#### Owns

- a distinct starting-assembly classification or metadata seam
- source-lane-safe representation for starting assemblies
- an honest action/read boundary for load-as-starting-configuration
- focused tests proving starting assemblies do not collapse into loose parts

#### Does Not Own

- adding all platform starting entries
- moving user-supplied files
- consuming loose XR/ADV assets
- wiring the full builder load runtime
- compatibility verdicts
- PubParts archive download or import

### Phase 1 Implementation Spec

#### Live Code Read

Current Catalog runtime has these relevant seams:
- `CatalogItemRecord.assetKind` separates `reference-asset` from `environment`; it should not become the starting-assembly discriminator because a starting assembly is still reference-like geometry/source content, not a third asset loader.
- `CatalogItemRecord.actionKind` currently supports `load-preview`, `add-to-project`, and `apply-environment`; no downstream owner exists for load-as-starting-configuration.
- `CatalogActionPlan` treats `load-preview` as preview-only, `add-to-project` as Browser project commit, and `apply-environment` as viewer environment ownership.
- `catalogSource.ts` passes repo seed fields into repo items and remembered imports, with source lanes kept distinct.
- `catalogShellShared.ts` owns mode/source/card copy, source-detail rows, filter/search helpers, and the existing wheel-fitment detail helper.
- `CatalogShellItemPage.tsx` renders metadata, helper-derived detail rows, notes, source details, and action buttons.
- Existing tests already cover contract guards, source snapshot pass-through, shared labels/filter/search behavior, item-page proof through `CatalogSurface.test.tsx`, and action-plan stability.

#### Decision

Implement Phase 1 as a contract and read boundary, not live assembly population.

Add a small explicit starting-assembly item role to `CatalogItemRecord`, with a helper that defaults existing records to the current loose/reference read:

```ts
export type CatalogItemRole = 'starting-assembly'

export type CatalogStartingAssemblyStatus = 'planned'

export type CatalogStartingAssembly = {
  status: CatalogStartingAssemblyStatus
  platformFamily?: CatalogItemPlatformFamily
  sourceAssetPreference?: 'step-or-stp'
}

export type CatalogItemRecord = {
  // existing fields...
  itemRole?: CatalogItemRole
  startingAssembly?: CatalogStartingAssembly
}
```

Implementation may choose equivalent names if local naming reads better, but the shape should stay narrow:
- `itemRole: 'starting-assembly'` is the runtime distinction from loose part listings.
- Absence of `itemRole` means existing standard Catalog behavior; no migration of every existing seed item is required.
- Do not add a literal `standard` role value in Phase 1 unless implementation proves the optional single-value role cannot support the UI/test read.
- `startingAssembly.status` starts as `planned` only because no load-as-starting-configuration owner exists yet.
- `startingAssembly.sourceAssetPreference` may record `.step`/`.stp` preference for repo-backed assembly assets, but it must not imply a source asset exists.
- `startingAssembly.platformFamily` may carry the intended broad platform family for future Phase 2 entries, but Phase 1 should not add real platform entries unless Manager explicitly approves them during implementation.

Do not use metadata-only as the main seam. Metadata rows are useful for display, but a first-class contract field is needed so future entries cannot silently read as ordinary loose part cards.

Do not add a new `CatalogItemActionKind` in Phase 1. Keep `CATALOG_ITEM_ACTION_KINDS` unchanged. Starting assemblies should remain preview/planned-read only until Phase 3 or a later downstream owner wires a real load-as-starting-configuration handoff. If a test fixture needs an action, use `load-preview` and prove no `add-to-project` or fake load action appears.

#### Runtime Difference From Loose Parts

A loose part remains a normal Catalog item:
- no `itemRole: 'starting-assembly'`
- normal system/part/platform metadata
- normal repo/import/external source semantics
- action behavior stays whatever the existing item declares

A starting assembly is a full-build/start record:
- has `itemRole: 'starting-assembly'`
- may carry `startingAssembly.status: 'planned'`
- may carry intended platform family and source preference metadata
- does not imply a Browser import, project commit, downstream builder load, or complete geometry unless a later phase explicitly supplies those owners and assets
- must not be created from loose XR/ADV files unless `Catalog-Gen2-4.5` classifies them as complete assembly-ready assets
