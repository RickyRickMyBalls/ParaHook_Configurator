### Purpose

This doc defines the architecture direction for the ParaHook `OutputPreview` family.

Use it to answer:
- what `System/OutputPreview` should own in ParaHook
- how accepted upstream slot sources should relate to published browser objects
- how collection-fed preview slots should read versus singular sources
- what belongs to `OutputPreview` surface polish versus shared publication/runtime contracts
- how future output-preview planning should be split into standalone shipped and future phase docs

### Why This Doc Exists

`Output Preview` is no longer only a small helper surface under the broader node-template lane.

The shared `Nodes-5` lane already proved the deeper contract work:
- `solidBodies` is now a first-class aggregate type
- `Output Preview` already accepts collection-fed `in:solid:*` slots
- grouped versus split publication is already explicit
- split publication already widens one accepted slot into many deterministic published object identities

What remains is now family-shaped work:
- the visible node surface still carries older one-slot-to-one-object habits
- accepted source rows, published object rows, and label editors need a clearer ownership split
- future enrichment should stay inside one dedicated `OutputPreview` family instead of reopening the broader shared `Nodes-5` contract every time the visible surface needs another pass

This doc exists so later output-preview work can land against one clear family index instead of being scattered across older shared-node notes.

### Scope

This doc covers:
- the future role of `OutputPreview` as the graph-owned publication surface
- the ownership split between accepted slot sources and published browser objects
- the visible collection-aware slot and child-object row direction
- the status structure for later `Shipped/` and `Future/` output-preview phase docs

This doc does not cover:
- re-deciding the shipped grouped-versus-split publication contract
- unrelated `Extrude` authored output semantics
- broader Browser/content hierarchy planning outside the node-owned preview/publication surface
- worker/export/runtime ownership beyond what `OutputPreview` needs to read honestly

- one input row equals one accepted slot source
