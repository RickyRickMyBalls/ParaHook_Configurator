## Doc Body

### Summary

`Nodes-5.3`, `Nodes-5.4`, and `Nodes-5.5a` already proved the deeper contract direction:

- one accepted `Output Preview` slot may take one atomic `solidBody` source or one aggregate `solidBodies` source
- one accepted slot may publish grouped as one object or split as many objects
- the lower layers already carry the needed publication facts
- the visible `Output Preview` node still retains older one-slot-to-one-object habits

The next honest family-owned step is therefore not another contract rewrite.

It is one visible-surface ladder that makes these distinctions legible:
- accepted source row
- source kind
- contributor flattening
- publication mode
- published object fan-out
- component versus row-owned child group ownership
- label/editor ownership
- convergence onto the same calmer structured-row template language already used by parent collection rows elsewhere in the node system

### Questions / Decisions

#### [ ] Question 1 - What should the top visible row mean?

##### Suggested answer
- one accepted slot source, not one published object

##### Why
- the slot is the graph-owned handoff boundary
- published objects are downstream results of that accepted source
- this keeps graph truth and publication truth separate but visibly connected

#### [ ] Question 2 - How should split collection publication read?

##### Suggested answer
- as child published-object rows nested under one owning collection source row

##### Why
- one slot can now legitimately fan out to many browser objects
- users should not have to infer whether many object rows came from one collection source or many unrelated connections

#### [ ] Question 3 - What should one active `SolidBodies` row own?

##### Suggested answer
- one row-owned flattened `SolidBodies` collection and one child publication group under the owning `OutputPreview` component

##### Why
- the `OutputPreview` node should remain the owner of one top-level component
- one active collection row may still accept many incoming `SolidBody` and `SolidBodies` wires
- those contributors should flatten into one authored collection at the row boundary instead of pretending each wire is a separate top-level component
- later grouped-versus-split publication can then stay downstream from that row-owned collection

#### [ ] Question 4 - Where should this first family slice stop?

##### Suggested answer
- at visible source/object row ownership, provenance readability, label/editor cleanup, and focused hardening

##### Why
- publication semantics already shipped
- accepted connection compatibility already shipped
- this family phase should stay on surface honesty rather than reopening deeper shared contracts

## Implementation Spec

Locked direction:
- one input row equals one accepted slot source
- `solidBodies` input should read as one collection source
- one active `SolidBodies` row may accept multiple incoming `SolidBody` and `SolidBodies` contributors
- those contributors flatten into one row-owned `SolidBodies` collection in authored row order
- singular `solidBody` input should remain calmer and simpler
- one `OutputPreview` node still owns one top-level component
- each active `SolidBodies` row owns one child publication group beneath that component
- published browser objects should render as child result rows beneath the owning source slot
- split publication should read as `one collection source -> many published objects`
- grouped publication should read as `one collection source -> one grouped published object`
- editor/label controls should follow ownership honestly:
  - source-row labels stay attached to accepted slot meaning
  - published-object labels stay attached to downstream object meaning

Locked boundaries:
- no new `publicationMode` schema work
- the first collection row may widen to true multi-wire acceptance for `SolidBody` and `SolidBodies` contributors
- multi-row top-level component splitting does not belong to this phase; multiple active rows still live under one `OutputPreview` component
- no `Extrude` row or output-contract changes in this family phase
- no worker/export/runtime ownership changes beyond exposing already-owned truth clearly to the node surface
