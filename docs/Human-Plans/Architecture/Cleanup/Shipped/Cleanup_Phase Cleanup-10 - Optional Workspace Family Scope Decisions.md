### Header

Purpose:
- force one explicit product and architecture answer for optional workspace families so `dashboard`, `notepad`, and `radio` stop shaping the core workspace architecture by implication

Owns:
- optional workspace family scope decisions

Does not own:
- workspace layout truth already locked in earlier cleanup lanes

### Why This Phase Exists

The cleanup vision already says optional surfaces need an honest product decision.

Current repo reality shows why:
- `dashboard` and `notepad` are already real `WorkspaceSurfaceKind` values
- both have real surfaces, detached-window hosts, stores, and persistence
- `radio` is still product-visible and shell-mounted through `RadioRuntimeHost.tsx` and `RadioPanel.tsx`
- but `radio` is not a `WorkspaceSurfaceKind`

That means the next problem is not taxonomy alone.

The next problem is scope honesty.

Without a cleanup lane here:
- shell wiring can keep implying that every mounted surface is a core pillar
- optional surfaces can keep accumulating persistence, commands, and host seams without an explicit product commitment
- `Radio` can keep sitting in the ambiguous middle where it is too real to ignore but still not classified as either a workspace surface or a consciously isolated runtime

This phase exists so we can:
1. lock the scope-decision boundary after the shipped workspace catalog work,
2. inventory the live optional-family coupling and ambiguity,
3. define one explicit optional-family decision rule,
4. prove that rule with one narrow live slice,
5. then hand later optional-family growth forward from an honest product-scope baseline.

### Scope

This phase covers:
- product-scope decisions for `dashboard`, `notepad`, and `radio`
- explicit classification of optional workspace surfaces versus optional background runtimes
- shell, workspace, persistence, and store coupling that makes optional families feel more core than they really are
- one narrow proof slice that validates the chosen optional-family rule in live code or docs

This phase does not cover:
- broad Dashboard feature redesign
- broad Notepad feature redesign
- broad Radio or Sampler redesign
- workspace shell/layout redesign
- a new workspace taxonomy pass
- optional-surface polish work that can wait until scope is honest

### Locked Direction

- optional-family scope must be decided explicitly in docs and architecture, not inferred from `AppShell` mounts or `WorkspaceSurfaceKind` presence alone
- `Cleanup 4A` remains the taxonomy and capability baseline:
  - `dashboard` and `notepad` are currently optional workspace surfaces
  - `radio` remains the main background-runtime mismatch input
- this lane may decide that a family is:
  - core and fully supported
  - optional and isolated
  - or retired
- if `radio` stays live without becoming a workspace surface, that should read as an explicit optional background-runtime decision, not as an accidental omission
- if `dashboard` or `notepad` remain optional workspace surfaces, their scope should be made explicit without letting them silently reshape core workspace assumptions
- this lane should prove one narrow scope decision before widening into broader optional-family cleanup

### Optional-Family Baseline

The working default for this lane is:
- preserve one explicit split between:
  - core workspace families
  - optional workspace-surface families
  - optional background-runtime families
  - retired or retirement-candidate families

Core families may:
- shape the shared workspace and shell direction directly
- justify broad ongoing feature growth

Optional workspace-surface families may:
- stay in `WorkspaceSurfaceKind`
- use normal workspace host modes and persistence
- remain available without being treated as the main product center of gravity

Optional background-runtime families may:
- remain product-visible
- remain mounted as focused runtime/tool systems
- stay outside `WorkspaceSurfaceKind` if that is the explicit decision

Optional families should not:
- quietly become core because they already have shell wiring
- keep accumulating architecture weight without an explicit support decision
- distort core workspace assumptions by accident
