### Purpose

This doc routes workspace layout and preference state that might later become canonical undo entries.

## Doc Body

### Owns

- durable project-authored or user-authored workspace layout settings after storage is explicit
- durable mode preferences after they are stable authored preference state
- exclusion proof that window/session navigation, focus/menu state, and transient panel interaction do not create canonical history entries

### Does Not Own

- active focus, open menu state, transient tab selection, window/session navigation, temporary panel size while dragging, keyboard dispatch refactors, command transcript, command recall, or runtime status
- Browser/project organization, Viewer Transform, Build Path UI, history panel UI, persistence architecture, checkpoints, optional branching, collaboration, or Gen 3 history UX

### Ownership / Storage Questions

- Are workspace layout and mode preferences project-owned, user-owned, or session-only?
- Which layout preferences are persisted today?
- Which changes are authored commits versus transient interaction frames?
- What is the commit boundary for resize, mode switch, dock, undock, reset, or preset actions?
- Can undo/redo restore only durable layout/preference state without rewinding focus, active menu, or current navigation?

### Acceptance Read

This candidate is implementation-ready only when a prep pass identifies concrete durable layout/preference owners, stable commit APIs, restore payloads, and focused exclusion proof for session navigation and local UI state.

### No-Widening Rule

Do not implement workspace layout/preference undo until ownership and storage are explicit. Do not capture focus/menu state, session navigation, window state, transient drag frames, keyboard dispatch behavior, or broad layout infrastructure.

First-pass decisions:
- Phase 1 should be proof-only. Workspace layout and preference state is durable in places, but its runtime commit boundaries are mixed with session/window routing and resize/drag frames.
- Workspace persisted layout and UI preference persistence are separate storage owners; later runtime phases must not use one full snapshot to restore the other.
- `activeViewerViewportId` is persisted to keep restored layouts coherent, but it should not be promoted as standalone undoable navigation without a later ownership proof.
- Viewport local-view/result/dock state overlaps Gen2-1 display/result/dock routing and should be proven as workspace-local preference state before runtime undo.
- Child-window/popup defaults and serialized popout descriptors are persistence facts, not sufficient proof that browser window runtime lifecycle belongs to canonical undo.
- Raw workspace and UI preference setters should remain history-free until explicit wrappers exist.
